# Model-card installation

A local model card supplies a user goal and curated model knowledge. The Agent chooses and executes installation as it would for the same direct chat request. The card does not select a fixed installer or require a fresh environment.

## Inventory diagnostics and direct generation results

The creation selector reads `/api/comfy/profiles?inventory=1`, which returns profiles together with completeness and per-path diagnostics. Incomplete Python/configuration evidence in one checkout does not hide profiles found elsewhere. An incomplete empty inventory is not reported as an uninstalled model list. The selector exposes **View model scan details** for copying the concrete affected paths/codes. Exact-name candidate indexes retain all matching paths, so a partial duplicate cannot overwrite a complete file in another location. Discovery remains unverified until real generation validation succeeds.

The inventory envelope uses the `creation.comfy-inventory` SWR key. Conversation selectors and operation cards retain the separate `creation.comfy-profiles` array contract. Installation completion refreshes both through the active cache provider. Sharing the old key between the two shapes caused beta.13 navigation and repair conversations to throw during rendering. A renderer error boundary now presents a reload action for unexpected route failures.

Model selectors group equivalent recipes by runtime/interpreter, component identity, workflow, bindings, capabilities and memory policy. Unchecksummed components retain pinned source identity; different precisions, workflows and independent environments remain separate. Grouping changes display only: all historical profile IDs remain in the service, selected profiles retain their own validation state, and existing jobs/bindings are preserved.

When the Agent uses direct ComfyUI HTTP generation, it retains the actual prompt ID and calls `openh3_comfy_observe_prompt`. This read-only adapter is independent of profile discovery, scopes the task to the trusted session conversation or creation request, persists monitoring and copies decoded outputs into application storage. It returns the same `comfyJobId` contract used by the normal conversation result component. Pending observations and saved results survive media-service restarts; the observer never submits or interrupts upstream generation and never certifies a profile. If handoff is unavailable, the Skill requires monitoring the same prompt and returning actual saved media links before reporting completion.

The primary action is **Start installation** (开始安装); verified profiles retain **Use model**. Repair and other-version actions preserve family, explicit profile choice and working environments. The editable prompt describes the desired outcome, reuse, repair and actual generation verification, without internal Skill/tool instructions.

## Target and execution

`useGuidSend` persists request identity, target and `installationMode: agent`, enables `comfyui-local` and scopes optional media tools. `prepareCreationEntry` binds context without detecting hardware or preparing an install plan. An unavailable optional local integration or missing profile does not prevent the original goal reaching the Agent for diagnosis, including older model-card contexts tagged as generation. Identity, selection and conversation conflicts still reject binding. A rejected initial message shows an error in the chat and restores its text and attachments into an empty composer for explicit retry; an uncertain send is never automatically replayed.

## Repair during generation

In full automatic mode the user's creative goal authorizes necessary compatible workflow, node and dependency repairs. The Agent diagnoses model capability, input bindings and runtime/node versions separately for image, video and multiple-reference requests. A missing binding is diagnosed before starting an unvalidated runtime; references are never silently dropped.

A fixed-profile repair requested from a generation conversation creates a persisted internal repair scope linked to that request. Reads, cancellation, recovery and terminal-result delivery work from the original request. The generation selection remains intact, actual session approval still applies, and changing the parent selection prevents stale repair writes. No model-card visit is required.

For a changed graph or runtime metadata, the Agent registers a new truthful profile variant, revalidates it using the original inputs, then invokes `openh3_comfy_profiles action=adopt-repair` with the successful job. Adoption requires the same request, unchanged selection, retained model components/precision, decoded outputs and a current validation fingerprint. It saves the active selection; the open conversation selector synchronizes that state without rebinding the old profile. Generation failures and variant-validation outcomes return to the original Agent even if the chat is not open. Successful validation must fulfill the original creative request or be followed by its completion.

The Skill directs the Agent to investigate supported adapters, workflows and permitted alternative routes when the existing profile cannot satisfy the goal. Routine repair does not ask for confirmation again; explicitly mandatory model constraints and actual runtime permissions remain binding. Installing an unconnected image loader is not evidence of reference conditioning or identity preservation.

Default workflows are starting recipes, not capability ceilings. Known missing bindings, disconnected references, missing nodes and workflow/schema revisions return `repair-workflow-and-continue` with the original ordered inputs and selected profile. The Agent checks existing variants and authoritative supported routes, installs matching dependencies, connects the actual conditioning graph, registers a variant, revalidates with the original request and adopts the successful repair in the same conversation. `automaticRetryAllowed: false` prevents unchanged replay; it does not prohibit diagnosed repair. A native input-adapter gap requires a supported adapter or an evidenced general-tool route with result observation; references may never be discarded to make a submission pass.

Observing a repairable generation failure no longer counts as resolving the goal. If the Agent becomes idle without starting related repair work, the persisted continuation delivers that failure once with its original inputs and profile. Active repair/preparation, newer related work, adoption, changed selection and explicit Stop suppress stale continuation. Selection comparison normalizes the stored schema so a restart changing JSON field order cannot strand a repair; actual selection changes still invalidate old work. This fallback requests an Agent continuation, not an automatic GPU resubmission or an unlimited retry loop.

Before submission, reference bindings must have distinct destinations for each supplied image. The final graph must connect every consumed reference node to an output declared by the live node schema (`output_node: true`). A disconnected input or an unconfirmed output schema returns a specific workflow diagnosis for repair before GPU submission. This proves structural participation only; an output preview or identity-preserving edit still needs the appropriate conditioning and result inspection.

The Agent owns its plan, inspection, recipe choice, commands, downloads and diagnosis. It uses normal Plan/Todo tools when present. The common work-progress panel remains generic; model cards do not impose stages or replace independent work. Progress and diagnosis remain in the conversation.

`openh3_comfy_model_guide` reads curated knowledge for any registered family. Its summary contains candidates, local reference paths and private Python/Git executables. A candidate ID returns exact components, provenance and a matching API graph or pinned UI template requiring conversion. It does not choose a recipe, probe hardware, execute commands or claim local verification. Direct conversations may read it without card binding.

Reuse compatible existing Python/ComfyUI and verified exact files. Choose dependencies from actual interpreter, driver, node-schema and kernel evidence. Core pins describe reference recipes; a different installed commit alone does not require a new environment. Adapted routes retain provenance and real validation.

Skill 2.0.8 applies the same execution policy throughout its model, source and environment references. General tools can install the confirmed runtime and nodes first, then inspect live schemas and construct the graph before GPU submission. Only the optional managed executor requires a complete graph in its submitted plan. Installation and capability repair may fetch pinned authoritative templates; ordinary generation reuses compatible graphs. Managed source-host allowlists constrain those APIs, while independently verified sources remain available through general tools under actual permissions.

A failed validation ends that attempt, not the user's goal. After the backend's unchanged-parameter OOM retry budget is exhausted, the Agent may diagnose and validate a materially different supported memory repair under existing authorization. It preserves required weights, precision and output requirements, records changes, and never adds another unchanged retry loop or competes with active or uncertain work.

## Generation monitoring and remaining work

For every generation request, including a single image or video, the Agent retains the real job ID and keeps its turn active until the actual terminal result. It uses `openh3_comfy_job_status` with bounded long polling (`waitMs: 30000`) or spaced status checks with backoff on older tools. An observation timeout is not a failed generation. The Agent explains real phase changes and repairs in the conversation, inspects terminal outputs, and continues any remaining authorized work. A result card does not replace this follow-through. Monitoring never requires another generation submission. Direct HTTP jobs must attach through `openh3_comfy_observe_prompt`, or continue through the same prompt's history and actual output retrieval if observation is unavailable.

At a terminal failure the Agent diagnoses and attempts a supported repair under the current authorization. A successful repair may recover the original failure only with matching request/selection, model and precision, submitted inputs and verified artifacts; unrelated successes do not hide failures. Explicit Stop pauses automatic continuation persistently. A later accepted user request resumes it using the saved control epoch; stopping a turn does not silently cancel an external generation. Actual tool/session limits must be reported with the existing job ID and unfinished work, rather than a false completion claim.

## Optional fixed executor

`openh3_comfy_install` remains available for suitable complete recipes. Calling it first is not required. Its command and transport allowlists apply to that executor, while ordinary authorized tools remain available. Inspect saved work before acting: active, awaiting-approval and unknown managed processes must not compete with another installer. After confirmed terminal failure, repair the affected step with general tools or recover the operation, preserving completed work.

Actual runtime approvals govern all writes. The fixed executor retains its UI confirmation and recovery budgets. Exhausting that executor does not prohibit a distinct, evidence-based permitted repair after its processes end. Integrity, source access, hardware requirements and other users' GPU work remain constraints. A command timeout requires process inspection before replacement.

An unknown existing environment by itself requires Agent diagnosis, not a reinstall. After an observed workflow-schema incompatibility, runtime replanning excludes that failed root even when its service has stopped. Other unidentified installations remain untouched and do not veto a separate application-owned runtime. Repair and explicitly selected profiles remain pinned to their environments. An occupied, unverified default runtime directory is not overwritten; the isolated fallback uses a stable request-specific sibling directory.

Compatibility preflight may start an approved runtime to read its live node schema. If it fails, it stops only the child started by that attempt, preserving external and previously running services. Unconfirmed cleanup blocks runtime replanning. Failed model-file repair restores quarantined originals and their source receipts when their original paths remain absent. If a replacement or concurrent file already occupies the path, both copies are retained and `restoration.json` records the conflict. These file safeguards are not a transactional rollback of Python packages, Git revisions or arbitrary commands.

The MCP adapter marks a returned failed operation as an error and includes its saved operation plus an explicit diagnosis-and-continuation action. Repeating `request` returns the same saved operation; it does not repair it. The Agent must inspect current state, diagnose and execute a permitted repair or use general tools after confirming that related managed work has ended.

## Application acceptance

Register the Agent-created component set as **downloaded**, with actual environment/node versions, component identities, workflow/hash and bindings. `openh3_comfy_profiles action=revalidate` schedules application validation and representative generation. Submission and downloaded files do not establish readiness.

Every subsequent profile-based generation also decodes its returned media before success and checks the dimensions, duration and audio contract actually bound by that profile. Frame-count bindings use the same frame alignment as submission. Ordinary creative requests use generation validation, which permits intentional solid colors, static scenes and silence; controlled installation smoke tests retain their additional content checks. These checks do not establish visual identity preservation or semantic prompt fidelity, which still require the Agent's result inspection.

`ComfyInstallContinuation` returns terminal installation-validation jobs to the original idle conversation, as well as managed-install results. It uses real job IDs and persisted delivery state with read-back after ambiguous sends. An unresolved `sending` record currently avoids replay but does not guarantee eventual delivery; reliable idempotent callback recovery remains an application limitation, not something Skill wording fixes. It does not invent an installer operation for native Agent work. Changed targets, cancelled conversations and unresolved remote generation never trigger another submission.

After success, `openh3_comfy_installation_complete` checks the request/family, successful validation job, verified profile and unchanged fingerprint. It records a completed Agent receipt with the existing **Use model** action. When Agent repair completed a failed managed task, that operation identity is retained. Failed, foreign, changed or merely registered profiles cannot be accepted. An Agent success message cannot set verified state.

If optional application integration is unavailable, the Agent may still install and test locally. It reports actual local verification separately from registration and never invents IDs or consent.

## Adding a family and validation

Use the shared Agent entry, guide, environment discovery, generation monitoring and repair contracts. Do not introduce a pre-Agent installer, fixed progress checklist or per-family forced pipeline. A new family still needs truthful model-specific integration data:

1. Register its schema ID, image/video kind, model-card metadata and guide reference together. Kind and card mappings must cover every schema family explicitly; an unknown video family must not fall back to image.
2. Describe each candidate's exact component roles, filenames, provenance/checksums, precision, runtime requirements and supported capabilities. A source-discovery candidate without a runnable recipe must remain unavailable for automatic installation.
3. Supply the matching API graph or pinned upstream UI template. Validate the whole packaged catalog, not only the first recipe for each family. Binding targets must refer to actual graph nodes and inputs; runtime/node pins, hashes and family ownership must agree. Reference inputs must be connected to a supported conditioning route; a placeholder or LoadImage node alone is not evidence of that capability.
4. Exercise installation, ordinary generation and repair with representative inputs. Include supported image/video/reference modes and required dimensions, duration and audio. Verify actual artifacts before marking the profile ready. Test missing dependencies, unavailable sources and interrupted monitoring without changing the user's goal or duplicating accepted generation.

Tests cover every family, matching recipes, unbound knowledge reads, unavailable optional binding, Agent registration/validation/completion without the fixed installer, rejected completion evidence and durable validation-result delivery. Controlled-engine integration tests do not replace real model generation on the target device.

## Portability and evidence limits

Application paths, selected interpreters and runtime endpoints come from the current installation and discovery evidence. A username, drive letter, the development machine's IP address, an available default port or a globally installed Python/Git must not establish compatibility. Reuse requires matching the actual runtime process, root and interpreter. Unknown or incomplete evidence is a diagnostic state, not permission to overwrite another environment or claim the model is missing.

Compatibility is specific to the selected recipe and device: operating system/architecture, driver, compute support, Python/Torch/kernel dependencies, memory, disk and live node schemas. A packaged application for an OS does not prove every GPU recipe runs there. Changed runtime, workflow or model evidence invalidates previous verification; transient free memory changes alone do not. Preserve the same accepted prompt across monitoring interruptions, and distinguish an unavailable result service from deleted media.

The current identity-based managed planner supports Windows/Linux x64 with NVIDIA compute capability 8 or later. Its new-environment recipe uses Torch 2.9.1/CUDA 12.8 and requires a driver major version of at least 570; new core revisions also require a pinned requirements digest. These are limits of that optional recipe, not evidence that an existing alternative runtime cannot work. The Agent may use an independently supported route with general tools, but AMD, Apple/MPS and other platforms are not certified by the NVIDIA recipe tests. New multimodal families also require an adapter for their actual input-node contract; the existing Omni adapter does not automatically implement other models' video/audio reference formats.

Filesystem fixtures, simulated hardware/service failures and catalog contract tests run without downloading models and belong in the ordinary test pipeline. The pull-request pipeline runs unit tests on Windows, macOS and Linux. Those tests establish contract behavior on their hosts, not GPU generation compatibility. Before advertising a newly supported model/platform combination, record the actual device/runtime, tested capabilities and successful decoded artifacts. Real generation evidence on one Windows GPU must not be described as verification of all machines or future models.

## Inventory after restart or reinstall

OpenH3 application roots use a complete asynchronous traversal without depth, entry, environment-count or 32-root-cache cutoffs. This includes the active data directory and its OpenH3/AionUi profile parent when applicable (covering both inner `OpenH3` and `aionui` layouts); the packaged installation/resources directory is excluded. Source markers identify ComfyUI independently of task names. Existing configured interpreters/endpoints are preserved; local or sibling virtual environments can supply an interpreter when unambiguous. Ordinary external roots retain bounded shallow discovery.

ComfyUI environments and known model filenames are indexed in the same filesystem pass. Runtime dependencies, generated media, logs, conversations, caches and output trees are skipped, while ComfyUI model folders and configured extra model paths are traversed completely. Incomplete scans surface as inventory errors rather than false not-installed results. Production diagnostics record the number of visited application files and total scan time without logging file contents or user paths.

The application traversal excludes dependency internals (`.git`, `node_modules`, `site-packages`, `__pycache__`), follows internal directory links with cycle detection, and does not traverse links escaping the declared application root. Application-owned installations also index all configured model subdirectories without the shallow external index's depth/entry limits. Inaccessible subtrees, unreadable model-path configuration and complete model sets with an unidentified interpreter report incomplete inventory rather than a false not-installed result. Inventory and installation planning share these application roots.

Matching complete curated component sets are discovered as downloaded. Known models registered by the Agent retain their actual recipes. An arbitrary weight filename, unsupported/unregistered model or previous output does not by itself establish a complete or currently verified model configuration. Successful generation and artifact validation are still required for verified state.

The existing H3 model set can reconstruct missing standard workflow profiles from packaged templates in an application-owned cache. Existing user workflows are preserved, and modified graphs retain their invalid/revalidation state. Inventory queries refresh discovery instead of using only startup state; a discovery error with no usable inventory returns unavailable rather than an empty not-installed list. Image and video model menus remain separate.

Historical H3 media playback first checks the application's artifact archive, then exact files under the configured runtime's output root, then the original service. Playing history never starts ComfyUI or submits generation. Newly completed jobs archive their output files in application data. Historical files recovered on playback are also archived and served with byte-range support. A missing original and missing archive are reported explicitly; a conversation record cannot reconstruct deleted media bytes.

## Multiple workflows per model

A model entry groups proven base component identities and precision. Each workflow keeps its own runtime, graph hash, input roles and validation. `identityRole: workflow` marks additional route weights; switching workflows does not replace the base model. Unknown component identities remain separate. Existing profile, job and artifact IDs remain valid.

Installation and inventory preparation materialize vetted lightweight graphs with available components. Missing nodes/weights remain explicit pending capabilities with download sizes. Optional preparation failures do not invalidate a working base route. The Agent owns dependency installation and repair using the model guide and normal tools. `openh3_comfy_resolve_workflow` separates read-only resolution from `action: prepare`; it does not invent model capabilities.

Generation supplies `input.requirements` and ordered, role-tagged references. Automatic selection prefers a matching verified route within the selected base model; fixed selection retains the exact environment/profile. Ordinary image-to-image, identity reference, style, structure, masks, and video frame roles are distinct. The current native multimodal adapter is FastH3-Omni; unsupported adapters remain explicit preparation requirements.

New callers provide a top-level `attempt: { taskId, attemptId, predecessorAttemptId? }`. A repeated attempt retrieves its persisted job across route arguments. A confirmed failed attempt can be repaired with an explicit predecessor; active or uncertain work must be recovered. Different tasks with identical prompts remain separate. The execution snapshot stores the actual graph and streamed copies/hashes of references in request-scoped storage. Running jobs retain their selected model and graph when the next-request default changes.

Successful result cards own the media preview. Agent Markdown that references the same exact archived artifact or scoped application job URL retains its caption without displaying the media twice. Ordinary links and unrelated media remain visible.
