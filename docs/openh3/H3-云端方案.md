# OpenH3 云端模型 API 商业化实施计划

**状态：** 方案草案，尚未实施  
**日期：** 2026-09-30  
**目标：** 以开源 OpenH3 客户端获取开发者用户，通过托管的对话模型 API 和视频模型 API 提供付费服务；不提供 GPU 租赁或 OpenH3 自营 GPU 推理。

## 1. 产品边界

OpenH3 提供统一的客户端体验和模型 API 接入服务。实际推理由上游模型/API 服务商执行，OpenH3 负责用户鉴权、模型路由、用量归集、额度控制、账单和用户支持。

```text
OpenH3 开源桌面端
├── 本地 H3 / ComfyUI：用户自己的机器和算力，不经过 OpenH3 Cloud
├── BYOK：用户自行配置第三方 Provider 和密钥
└── OpenH3 Cloud：用户账号的短期访问凭证
    └── OpenH3 API 服务
        ├── 对话模型 API Gateway -> 上游 LLM Provider
        ├── 视频模型 API Adapter -> 上游视频 Provider
        ├── Auth / Entitlement / Usage / Credit
        └── Payment Provider / 支付回调
```

明确不做：GPU Worker、GPU 秒出租、托管 ComfyUI、本地任务失败后自动转云、客户端内置共享上游 API Key。用户必须主动选择云端 Provider；提交前说明所用模型、输入素材传输范围、计费单位和费用上限。

## 2. 计费原则

不能将所有能力都折算成 Token：对话 API 有输入/缓存/输出 Token；视频 API 可能按生成次数、秒数、分辨率、模式或厂商报价计费。保留上游原始 usage 和成本字段，再映射为 OpenH3 的统一额度单位（暂称 Credits）。

每个 Provider Adapter 提供版本化的价格表和估算器：

```text
estimate(request, priceVersion) -> { estimatedCredits, assumptions, expiresAt }
measure(response) -> { providerUsage, providerCost, usageConfidence }
settle(reservation, measuredUsage) -> ledgerEntries
```

规则：

- 先展示预估费用与用户设定的单任务上限，再创建计费预留；不得在任务执行中突破授权上限。
- 调用成功按可获得的真实用量结算；厂商不提供精确用量时，使用公开、可解释、版本化的 OpenH3 定价规则，并标注估算口径。
- 请求失败、厂商拒绝、超时结果不明、用户取消分别定义结算策略；禁止把不确定状态直接当成功或直接重复扣费。
- 以 OpenH3 request/job attempt ID 做幂等；重试创建新 attempt，保留与父任务的关联。
- Credits 是产品内部用量单位，不在技术方案阶段承诺货币汇率、永久有效或可提现；套餐、税费、退款和法律条款待商业/法律确认。

## 3. 开源复用评估

| 项目 | 可复用能力 | 许可证/成熟度注意 | 方案取舍 |
|---|---|---|---|
| [LiteLLM](https://github.com/BerriAI/litellm) | LLM 统一接口、OpenAI 兼容 API、Provider 路由、虚拟密钥、用量/成本记录、限额等 | 主仓库 MIT 范围与 enterprise 目录需逐项确认；供应商定价/模型支持变化频繁 | **推荐用于对话模型 Gateway 试点**。只让后端访问它；不要把其虚拟 key 当 OpenH3 用户账本或完整订阅系统。固定版本并做安全评估。 |
| [OpenMeter](https://github.com/openmeterio/openmeter) | CloudEvents 用量事件、Meter、Entitlement、计量查询及订阅/账单相关 API | Apache-2.0；官方 README 标注 releases 为 beta，需验证当前版本和生产运维要求；不是支付处理器 | **推荐作为用量计量/额度基础设施 PoC**。先验证 reservation、并发限制、回放和事件幂等；若不足，OpenH3 自有 ledger 是扣费真相源，避免把计费正确性押给 beta 功能。 |
| [Lago](https://github.com/getlago/lago) | Metering、套餐、预付额度、entitlement、发票和支付集成，带运营 UI | AGPL-3.0；网络服务修改和嵌入/白标使用需做许可证审查 | 功能覆盖度高，但不作为默认首选；只有法律审查接受 AGPL 义务或取得商业授权后再选。不要同时部署 Lago 和 OpenMeter 做重复计量。 |
| [Keycloak](https://github.com/keycloak/keycloak) | OIDC/OAuth、用户会话、设备登录、组织身份基础 | Apache-2.0；部署和升级有明显运维成本 | 作为身份标准和自托管候选，不默认在 MVP 自建全套 IAM。优先兼容 OIDC Authorization Code + PKCE，身份服务可替换。 |
| [Stripe Billing](https://github.com/stripe) / 支付服务商 | 订阅、支付、退款和 webhook | Stripe API/服务不是可自托管开源实现；地区、商户资格、费率与支付方式须以实际账户为准 | 将支付放在独立 Payment Adapter。先确认公司主体和目标市场，再选择 Stripe、国内合规支付机构或人工试点；不把支付供应商当 usage ledger。 |

建议组合：**LiteLLM（对话 API） + OpenH3 自有薄层 API/BFF 与计费预留接口 + OpenMeter PoC（用量聚合/entitlement） + 独立支付适配器**。视频 API 通过 OpenH3 自有 Adapter 处理异步任务，因为视频厂商的提交、轮询/webhook、取消、素材上传和 usage 语义通常不同；不强行塞进 LLM Proxy。

如 OpenMeter PoC 不能满足强一致额度预留与并发扣减，先以 PostgreSQL 事务账本实现最小可靠核心，再异步镜像事件到 OpenMeter；不能并行维护两份互相竞争的余额真相源。

## 4. 服务端职责和最小数据合同

推荐先沿用 OpenH3 的 TypeScript 技术栈建立独立云端服务边界；部署形态、云厂商和数据库托管方案在容量/合规需求明确前不锁定。客户端现有 JobStore 仅管理本地/桌面任务，不可作为云端账务数据库。

云服务最小模块：

1. **Identity Adapter**：OIDC 登录、短期 access token、refresh token 轮换/撤销、设备会话；桌面端使用 PKCE，不嵌入服务端密钥。
2. **API Gateway**：鉴权、用户/套餐策略、速率和并发限制、请求体限制、request ID、超时、上游 Provider 路由和脱敏日志。
3. **LLM Adapter**：统一 OpenAI-compatible 请求/响应，保留模型、输入/缓存/输出 Token、上游 request ID、价格版本和错误类型。
4. **Video Adapter**：统一创建/查状态/取消/取结果接口；持久化上游任务 ID，支持 webhook 或有退避上限的轮询，去重回调；计量记录模式、分辨率、时长、厂商返回用量和结果状态。
5. **Usage & Ledger**：事件幂等、额度预留、结算、释放/退款和审计；不可只维护一个可覆盖余额字段。
6. **Catalog & Pricing**：模型能力、地区可用性、计价维度、成本价、销售价、版本生效时间；所有估价与历史消费都引用 immutable price version。
7. **Payment Adapter**：订单、支付意图、签名 webhook、退款与对账；支付成功事件幂等，绝不从客户端声称的支付结果加余额。
8. **Operations**：上游失败率/延迟/成本、用户支出、异常调用、对账差额、退款队列和人工封禁审计。

建议的逻辑实体（不要求全部独立成表）：

```text
account, device_session, plan, entitlement
provider_model, price_version
api_request, video_job, video_attempt
usage_event, credit_reservation, credit_ledger_entry
payment_order, payment_event, refund, audit_event
```

关键不变量：

- 所有收费请求在服务端生成唯一 `requestId`；视频任务另有 `jobId` 与 `attemptId`。
- `credit_ledger_entry` 追加写；余额由账本和有效预留计算/物化，所有结算可追溯。
- 预留和最终结算支持幂等重放；并发请求不会超卖额度。
- 未知上游状态进入 `reconciling`，先查上游状态再决定结算或释放，不能盲目重发可能产生费用的视频请求。
- 原始提示词/素材默认不进入长期运营日志；按最小必要原则保存任务运行所需数据，设置 TTL、删除和导出规则。

## 5. 桌面端产品体验

在现有 Provider 选择和对话设置上扩展，不重建客户端：

- Provider 选项：本地 H3、用户自定义 Provider、OpenH3 Cloud。
- OpenH3 Cloud 登录后显示套餐、可用额度、消费明细入口和预算设置；未登录仍可使用本地模式和 BYOK。
- 视频任务提交前显示 Provider、模型、输入素材是否上传、预计额度区间和单任务最高额度；用户主动确认。
- 任务卡显示实际使用量或“待上游结算/估算值”，任务失败可查看退款/释放状态。
- 增加每次任务和每月预算上限、余额告警与关闭云端调用开关；不得本地任务失败后自动转云并产生费用。
- 安全储存 OpenH3 refresh credential；绝不把厂商 API Key 或服务端 master key 写入源码、日志、安装包或 renderer。

## 6. 阶段路线与验收门槛

### C0：Provider 与商业/合规决策

- [ ] 选定首发市场、用户群、上游对话/视频 API、供应合同、可服务地区和支持的数据处理边界。
- [ ] 建立模型能力/成本矩阵：调用方式、用量返回、异步状态、取消语义、数据保留、速率限制、重试规则和条款。
- [ ] 对商业 API 聚合/转售、用户内容处理、隐私、消费者退款、税务、发票和开源许可做专业审查；未确认前不宣传具体商业承诺。
- [ ] 对比 OpenMeter 当前 release、并发 entitlement 与事件去重；验证 LiteLLM 支持的每个目标 Provider 及定价映射。

**门槛：** 至少确定一个对话 Provider 和一个视频 Provider，拿到可用于服务端托管的 API 权限及其商业使用条款；确认故障、取消和费用语义。

### C1：内部 LLM API Alpha（先不收款）

- [ ] 实现 OIDC/PKCE 登录和服务端短期 token，客户端不接触上游密钥。
- [ ] 部署 LiteLLM 隔离环境，封闭管理端口，仅由 OpenH3 Backend 调用；设模型 allowlist、用户级 key、预算和限速。
- [ ] 增加 OpenH3 Cloud Provider 配置、流式对话代理、request ID、脱敏日志和基础调用用量事件。
- [ ] 做用户隔离、并发、超时、上游 429/5xx、密钥轮换/撤销和审计测试。

**门槛：** 桌面端可登录并通过 OpenH3 服务调用模型；安装包和客户端网络抓包无上游 API Key；所有调用均能归属到用户并从上游账单核对。

### C2：视频 API 试点与任务一致性

- [ ] 针对一个视频 Provider 实现 Adapter：创建、状态回调/轮询、取消、结果代理下载、失败分类和回调验签。
- [ ] 将云端视频任务映射到独立的云 Job 表，不把本地 ComfyUI JobStore 当云端真相源；桌面侧继续使用统一视频任务 UI。
- [ ] 对每个收费任务先 reserve，再按终态 settle/release；未知上游状态进入 reconciliation，不自动重复生成。
- [ ] 限定上传类型、大小、生命周期和访问签名；验证用户删除、链接过期、跨用户 IDOR 与内容泄露。

**门槛：** 成功、失败、超时、用户取消、重复 webhook、客户端断线和服务重启各跑完整测试；账单事件不重不漏，且可与 Provider usage/账单核对。

### C3：额度账本和限额（先赠送/内部试用）

- [ ] 选定单一计量真相源：完成 OpenMeter PoC 决策；不满足强一致 reserve/settle 时使用自有 PostgreSQL append-only ledger。
- [ ] 设计 Credits 定义和价格版本；分别支持 LLM token usage 与视频 Provider 的原生计价维度。
- [ ] 实现预留、结算、释放、退款、赠送额度到期和人工调整；财务调整必须写审计原因和操作者。
- [ ] 实现账户额度、任务上限、日/月预算、并发上限、速率限制及欠费硬停止。
- [ ] 后台提供只读用量/异常查询和账单导出；不先造完整 CRM/财务系统。

**门槛：** 属性测试/并发测试证明不超扣、不负余额、不重复退款；每一分钱/点数都可追溯至请求、价格版本和 Provider 证据。

### C4：订阅、充值与正式收费

- [ ] 确认公司主体、目标市场、税务/发票和支付渠道，比较 Stripe Billing 等服务与目标地区合规支付服务。
- [ ] 接订单和支付回调；校验签名、时间戳、事件 ID 和金额/币种；对账后再发放 Credits。
- [ ] 订阅包含额度、按量超额、预付包三种方案分开建模；先以简单透明的两档套餐试点，不承诺无限调用。
- [ ] 增加取消订阅、退款、争议、重复扣款、支付失败、补偿额度和客服申诉处理。
- [ ] 灰度开放、设日成本熔断和单 Provider 总支出阈值；实际价格随 Provider 变更须有版本与用户告知。

**门槛：** 沙盒支付、webhook 重放、退款和月结对账通过；客服可从订单追到 usage event、provider request 与账本变动。

### C5：开发者平台与规模化

- [ ] 公开 API 文档、SDK/示例、模型能力与地区列表、错误码、速率限制和状态页。
- [ ] 提供用户 API keys（只能映射到用户权限，不能等同上游密钥）、撤销、预算、用量查询和审计导出。
- [ ] 团队/组织共享套餐与预算；只有个人版 unit economics 和客服负载验证后再做。
- [ ] 建立 Provider 熔断、路由降级、配额同步、成本告警、数据保留策略和事故响应。
- [ ] 开源客户端发布流程中固定 Cloud API 协议版本；Cloud 服务作为独立仓库/私有服务维护，开放协议不泄露服务端密钥和风控逻辑。

## 7. 建议的最小首发范围

1. 免费开源桌面端继续支持本地 H3 与 BYOK。
2. OpenH3 Cloud 首先提供一个对话 API 和一个视频 API；初期人工开通/邀请制，不做公开充值。
3. 后端用 LiteLLM 复用对话 Provider 适配，视频使用薄 Adapter；先记账和赠送额度，不接支付。
4. 完成用户级用量、成本和限额的真实对账，再决定 OpenMeter 接入深度和收费方式。
5. 支付选型及各地区开票、退款、隐私义务由公司主体和目标市场决定，不在客户端中耦合具体支付 SDK。

这样先验证用户是否愿意为“免配置的对话 + 视频模型 API”付费，再投入支付、团队后台和复杂订阅系统，避免先重复建设完整商业平台。

## 8. 当前不建议做的事

- 不自建 GPU 集群或承诺本地 H3 自动转云。
- 不在客户端分发共享 Provider Key，不以混淆、加密常量或隐藏配置作为密钥保护。
- 不只按 Token 计量视频，不在 API 无真实 usage 时假装精确到分。
- 不在 LiteLLM、OpenMeter、Lago 之间同时维护套餐、余额和扣费真相。
- 未审许可证前不将 AGPL Lago 嵌入或白标进商业产品；不因项目开源就假设允许模型 API 转售。
- 不先做复杂组织、Marketplace、自动充值和无限套餐；不允许未知结果状态自动重试付费视频生成。

## 9. 指标与决策门槛

试点期按周观察：登录到首次成功调用转化率、对话和视频 API 成功率、P50/P95 延迟、Provider 429/5xx、单用户成本、成本/收入毛利、额度争议率、退款率、任务取消率、支出熔断次数、隐私/安全事件、支持工单量。

进入收费前必须具备：明确的上游商业授权、可验证的用量/成本对账、预留和幂等结算、硬预算熔断、账单导出、退款流程、隐私与数据保留说明、Provider 密钥轮换和事故响应手册。
