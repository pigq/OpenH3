# Local ComfyUI

## Own the installation goal

A model card is a shortcut to the user's goal and curated model knowledge. It does not select an installer, require a fresh environment, or limit your command/file/web tools. Use the same reasoning and execution strategy as a direct chat request to install that model. Preserve the user's actual goal and explicit constraints. A generation intent does not prohibit the repairs needed to finish generation. Future model cards follow the same process.

Apply the user's current instructions and actual tool permissions throughout. References describe model facts and executor protocols; they must not add a fixed-installer prerequisite, a model-card visit or a new chat-confirmation gate. Stop a failed step to diagnose it, not the whole goal when a supported repair remains available.

Follow a new explicit installation target in the current conversation even when its family differs from the earlier creation selection. Read that family's model guide directly. For the optional fixed executor, send the actual `family` with `intent=install` or `install-other`; the application creates a linked installation without changing the earlier generation choice. For installation with general tools, pass `installationIntent=install-other` on both `openh3_comfy_profiles action=register` and `action=revalidate`, then call `openh3_comfy_installation_complete` with the successful validation job. This path does not require starting the fixed installer. These intents describe the user's current goal; they do not grant permission or permit silently substituting another model for a mandatory generation choice. Keep current session approval and report the actual installed model. An old selection mismatch is not a reason to send the user back to a model card.

Start with a short acknowledgment and a task-specific plan based on the goal and evidence. Use the session's Plan/Todo tool when available so the normal work-progress panel reflects your real plan. Update that plan when diagnosis changes it. The application must not manufacture a fixed checklist. Without Plan tools, keep a short checklist in conversation and continue execution.

Inspect prior installation/validation jobs before new execution. Use `openh3_comfy_install action=status` when an operation or ambiguous previous submission is present. While a managed operation is active, awaiting approval, or of unknown status, do not run another installer. Confirm terminal state before taking over a failed step with general tools. Preserve downloaded files, receipts, checked-out source and working environments.

## Inspect, choose, execute and repair

1. Read `openh3_comfy_model_guide` for the selected family. Its summary gives candidate options, local reference paths and available private bootstrap tools. Request a candidateId for exact component identities, provenance and matching workflow. These are recommended complete recipes; they do not establish local compatibility or require replacing a core because its commit differs. If the guide is absent, use permitted Read/command tools to inspect the relevant references and catalogs.
2. Inspect profiles and actual environments with `openh3_comfy_profiles action=list`, `openh3_comfy_environment` and/or command/file tools. Check installed/running ComfyUI paths, actual Python, GPU/driver/free VRAM/RAM/disk, dependencies, node schemas, model locations and previous outputs. Start with known/configured paths and relevant processes. Reuse compatible environments and verified exact model files. Missing evidence needs diagnosis; missing dependencies are installation steps, not automatic hardware rejection.
3. Choose an appropriate model/precision/workflow from the user's target and measured evidence. Unless the user selected a precision/version, choose the practical compatible route yourself and explain it. Keep Base/SFT, Turbo/Raw and diffusion/encoder/VAE sets distinct. For adapted or newer supported workflows, pin provenance and dependencies, inspect the actual node schema and record the actual graph and versions. Do not invent compatibility or silently change original parameters after a failed generation.
4. Execute with command, file, HTTP/download and process tools actually available. You do not need to call `openh3_comfy_install action=request` first. The fixed installer is an optional executor when its complete recipe fits this machine; it is not a prerequisite for ordinary tools. After a confirmed terminal installer failure, inspect its logs and continue the same goal through an evidence-based repair with permitted tools. Do not restart all work or return only instructions for the user.
5. Save an installation journal in the scoped workspace: source revisions/hashes, paths, download receipts, commands/versions, progress, live process IDs and validation prompt/job IDs. Use real background/process tools when present. A command timeout does not prove the process stopped: inspect process/output state before retrying. Otherwise make long transfers resumable and bound each command; never invent process tools. Keep progress and diagnosis in conversation. Continue until verified success, user cancellation or a concrete blocker that cannot be resolved with available tools and grants.

Prefer domestic verified transports, then primary sources. A failed URL does not prove the model unavailable: use `openh3_web_search`, `openh3_web_fetch`, `openh3_comfy_sources` and available equivalents to find exact official artifacts and verify repository metadata. A matching name or size is not identity. Preserve fixed revisions, SHA-256, resumable receipts, source access and license requirements. Managed sourceOverrides accept ModelScope, hf-mirror.com and huggingface.co; that executor's host allowlist does not prohibit an independently verified primary source through authorized general tools.

Windows includes private full Python and Git; the guide reports their absolute paths. Use the full Python to create isolated venvs when needed. Verify venv/ensurepip/pip before resolving binary wheels, and re-resolve wheels when changing interpreter. Never copy missing standard-library modules into an embedded Python. Do not change system PATH or unrelated environments to compensate for a missing command.

General-tool installation may proceed in stages: install the confirmed runtime and required nodes, read their live `/object_info`, then construct and validate the graph before submitting GPU work. A complete offline graph is required by the optional managed plan protocol, not before this authorized staged installation. Do not create a redundant runtime merely to satisfy a planner.

The user's installation request authorizes that task's scope; actual runtime permissions still apply. Reuse grants and use normal approval tools when required. Full automatic mode needs no extra chat confirmation. A denied permission, integrity mismatch or source-access restriction must not be routed around with Shell. `COMFY_APPROVAL_MODE_UNAVAILABLE` means permission lookup failed: inspect service/session health and retry the same request after recovery, without fabricating an approval mode or starting an alternative mutation while authorization is unresolved. A confirmed device limitation excludes that unsupported route; investigate supported routes within the user's constraints. Recover active or unknown GPU work before resubmission; never kill another application's process or clear another user's queue.

## Verify and make the model usable

Prepare the model guide's complete `recipe.workflows` set for the selected exact model candidate, keeping `recipe.workflow` as its default. Follow [workflow preparation and routing](references/workflow-routing.md): share weights and compatible runtime/nodes across lightweight `with-base` variants, install large additional control/patch/adapter weights on demand, and preserve each graph's independent preparation and validation state. The catalog provides recipes and dependency accounting; the Agent chooses and executes the installation plan. A pending optional capability does not invalidate a verified default.

Use `openh3_comfy_resolve_workflow action=prepare profileId=<installed profile>` when the preparation result is not already available after registration/installation. Inspect its prepared routes and `pending` dependency reasons. Its default `action=resolve` only reads candidates; preparation writes graphs using existing weights and does not download models or start GPU work.

The guide includes an optional local validationReference image for editing/reference-model smoke tests when the user has not supplied one. Use it as a test input, not as the user's creative source.

After installation, run imports/kernels and inspect actual ComfyUI `/object_info`. Exercise the selected graph with a representative image/edit/video and retain parameters, output paths and prompt IDs. Files existing or a running service are not proof of readiness.

Register the real component set, environment, workflow path/hash, bindings and actual runtime/node versions with `openh3_comfy_profiles action=register`, as downloaded. Never set verified yourself. Then call `action=revalidate` with profileId and representative smokeInput. The application schedules real validation and generation, returning comfyJobId, job and validation:true. Keep the Agent turn active and monitor that same job with `openh3_comfy_job_status`, using `waitMs: 30000` when supported. Inspect terminal output before reporting completion. On failure inspect the job/log, repair the affected layer and revalidate without duplicating active or uncertain generation. Application continuation is a recovery fallback if the session is interrupted, not an instruction to finish early.

Sharded models use the actual indexed weight files, not a folder treated as one file. Follow [install evidence](references/install-evidence.md) when completing per-file metadata or repairing legacy directory registration. Revalidation also starts and owns the selected ComfyUI service; use that lifecycle when an ordinary shell launch does not persist.

The curated model cards are recommendations, not a registration whitelist. For any user-requested local image or video model outside the directory, use its real stable lowercase family slug (for example `qwen-image`), display name, fixed version and explicit `kind: image|video`; never relabel it as Qwen-Edit or another built-in model to pass registration. An empty model guide means no bundled recipe: research and configure the actual supported runtime/workflow using normal tools, then register and validate through the same interfaces. Registration persists the model in the image/video selector and model manager. Use `installationIntent=install-other` when configuring a new target in an existing or general conversation. Ordinary chats register, revalidate and complete through their conversation context; no model-card request or manual registry editing is required. A successful direct ComfyUI call or observed output alone does not register a reusable model: finish registering its real reusable workflow and verify the returned inventory entry before reporting configuration complete. Cloud API models belong in cloud connection settings, not a local ComfyUI profile.

After success, inspect the verified profile and artifacts, then call `openh3_comfy_installation_complete` with the real jobId. The backend rechecks this request/family, successful job and unchanged fingerprint, then records a receipt with the application's Use model action. Report actual model/version/location and output evidence. This completion tool cannot manufacture validation or approval.

For a model-card repair that changes the graph or runtime/node metadata, preserve the old profile and register the actual repaired variant under a new profile ID. Revalidate the variant, then use `openh3_comfy_installation_complete` with its successful jobId in the same repair request. Completion preserves the original model components and precision, checks that the request selection has not changed since validation began, and activates the verified variant. `action=adopt-repair` is for an existing generation request; a model-card repair finishes through the completion tool.

Direct conversations use their conversation scope for model registration, generation and managed installation. Use the actual registered profile IDs and returned job IDs; the application creates its own internal request scope.

## Optional managed executor

`openh3_comfy_install` remains useful for complete fixed recipes and resuming saved managed work. Identity requests let that executor prepare its plan; complete plan payloads are also supported. Full-auto starts a valid approved plan; other modes confirm the saved plan once in the card. Remain engaged and inspect the same operation with bounded spaced status checks, then inspect terminal events. Await user input only when the existing consent card requires it. Application continuation is a fallback for an interrupted session. Diagnose actual errors, not the default environment's expected missing-Python state.

Known runtime/schema, venv or legacy Git failures may automatically replan under automatic approval. Otherwise recover the operation after a relevant repair. Managed execution budgets allow two recoveries per failed stage and ten overall, stopping repeated unchanged failures earlier. Exhausting that executor does not prove the original goal impossible: once terminal state is confirmed, continue with a different permitted evidence-based route, preserving completed work and actual permissions, integrity and device requirements.

## Generate with the selected profile

Ordinary chat is a complete generation entry point. When no model was explicitly selected, inspect registered profiles and choose a suitable image/video model for the user's goal. Pass its `profileId` to resolve and generate; the application attaches jobs to the current conversation. An image prerequisite and the final video may use different models. When a model card supplied a selection, preserve that choice. A plain-chat repair can register a corrected variant and generate through its returned ID; do not invent a request ID or ask the user to revisit a model card.

For a story or multiple outputs, plan the whole deliverable, choose shot lengths supported by the actual model, and keep a small shot manifest with prompts, job IDs, output paths and completion state. Generate and inspect the first real shot, then continue the remaining shots while reusing the working runtime. After generation, edit the clips into the requested duration, add the intended sound/music with available tools, verify the final file and deliver it. A saved script, storyboard, first clip or queued job is an intermediate result. Use command/file tools for editing and audio when no dedicated tool is exposed. Keep reusable character/scene references when supported. Do not create a fixed number of shots, fixed model or fixed duration for every request.

Before submission, determine the task and every reference's semantic role and call `openh3_comfy_resolve_workflow` using the live tool schema. Read [workflow preparation and routing](references/workflow-routing.md) for the input/count contract, missing-capability preparation and task/attempt continuity. Route within the selected model set and precision; respect an explicitly fixed workflow. Missing supported capabilities must be prepared, registered and validated in this conversation while continuing the original goal. Do not submit a known incompatible route or substitute ordinary image-to-image for identity preservation.

Use the currently selected registered profile. A downloaded or discovered profile may generate: the backend validates it with the user's actual request and marks it verified only after successful output validation. Do not turn generation into installation or repair merely because a profile is not yet verified. If selection is absent or may have changed, call `openh3_comfy_profiles` with `action: list` once and use its authoritative `selection` together with `profiles`. `COMFY_SELECTION_CHANGED` requires checking the new selection and preserving the user's choice.

Submit `openh3_comfy_generate` with `profileId` and `input`. The backend performs runtime, queue, device, node/schema, media, and binding preflight. Do not repeat raw `/system_stats`, `/queue`, `/object_info`, Python/Torch scans, catalog reads, model hashing, installation, or graph construction before each generation. Never clear another job's queue or silently switch the model, source, precision, dimensions, frame count, batch, or quality.

For task continuity, also pass the top-level `attempt: { taskId, attemptId, predecessorAttemptId? }`. Keep the same IDs after a lost response; resolve does not create them. Use a new attempt only for a confirmed failed predecessor, and a new task for a separately requested output. Preserve the real returned job ID and recover uncertain work.

Keep ordered local image/video/audio attachment paths in `input.references` with stable `id`, `type`, `path` and semantic `role`; masks also name their source with `maskFor`. Legacy `{type, path}` and `imagePaths` remain readable, but missing semantics are not evidence for identity/editing support; never combine references and imagePaths. Preserve supported profile capabilities and bindings. FastH3-Omni needs at least one image or video reference. For FLUX 3 Image Klein, expand the request into a coherent full scene caption while preserving subjects, counts, composition, requested style, and exact rendered wording. Keep MOSS Base/SFT and Krea Turbo/Raw separate.

## Repair capabilities to finish the original goal

Treat missing workflow nodes, image bindings or capabilities as a diagnosis to solve, not a reason to send the user back to a model card. This applies to text-to-image, image-to-image, text-to-video, image-to-video and multi-reference tasks across all model families. In full automatic mode, install relevant missing nodes/dependencies, adapt the graph and validate without asking for confirmation again. Explain material changes while continuing the user's goal.

The shipped baseline is not the model's capability ceiling. When the request includes references or asks for a new capability, first inspect relevant registered variants and local workflow bindings against the requested reference roles. Reuse that evidence; query the selected runtime's `/object_info` only for missing or uncertain nodes. If the saved graph cannot consume the input, investigate an upstream-supported image-to-image, structural control, editing or video route for the actual selected weights. A catalog with only a t2i recipe does not justify refusing the request or repeating that recipe. Use family references as research starting points, then pin the chosen official graph, extra components and dependencies. For Z-Image, use the reference-capability routes section in the [image-family guide](references/z-image.md).

Distinguish model capability, saved workflow capability, missing node implementation and runtime revision mismatch. A t2i profile name alone does not prove the model cannot use references. Inspect a proven upstream graph and actual `/object_info` only for the affected layer. If the model supports the required route, install the compatible node revision and its dependencies, preserve model weights/precision, and build a complete connected graph with real input bindings. Merely adding LoadImage does not create image conditioning or identity preservation. Multi-reference requests must consume all references in their original roles and order; never drop references, arbitrarily merge them, or silently replace image-to-video with text-to-video. Keep the requested aspect ratio, duration and other output requirements.

Capability errors end that attempt, not the goal. Diagnose whether the missing part is a binding, dependency, adapter, or model feature; do not resubmit unchanged input until that part is repaired. Retain the original reference roles and inspect the generated result for the requested content. A connected graph and decoded output prove execution, not identity preservation or faithful edits. If evidence rules out one route, continue investigating other supported routes within the user's constraints before declaring a blocker.

A reference-conditioned model can fulfill an original text-only creative goal through an intermediate image. For FastH3-Omni, `COMFY_OMNI_REFERENCE_REQUIRED` / `action=prepare-reference` means prepare a real reference, not automatically ask the user to upload one. If the goal is an invented scene (for example a dusk city skyline), use an available image model/tool to create a suitable scene reference under current authorization, inspect and save the actual image, then continue with the selected Omni model, `reference-to-video`, and the original duration/aspect ratio. Explain that you generated the intermediate reference. Use general tools for this prerequisite when the final-video selection scopes native generation tools to Omni; observe the real image prompt and retain its path. Do not replace the final model, use a smoke fixture, or represent generated media as a user upload. When the user requires a specific person, supplied source, exact original, or explicitly forbids synthesized references, recover that real attachment or ask only for the missing source. A missing image tool/model is a prerequisite to diagnose or prepare within the user's constraints, not proof that every text-only request needs an upload.

For `COMFY_INPUT_UNSUPPORTED:<parameter>`, resolve or repair the actual binding before submitting; preserve requested dimensions, duration and other parameters. For `COMFY_SMOKE_VIDEO_INVALID` / `COMFY_SMOKE_IMAGE_INVALID`, inspect `diagnosis.action`, the saved file and ComfyUI history before another generation. The code also covers real user output validation: it does not establish that GPU generation failed. Compare actual dimensions, graph-aligned frame count/duration and required audio, and fix the affected graph or validator contract; do not repeat an already successful expensive generation to fix presentation or validation.

The native video/audio reference adapter currently supports FastH3-Omni only. For other families, do not remove or bypass the `COMFY_MULTIMODAL_WORKFLOW_REQUIRED` rejection, relabel media as images, or invent native bindings. When an authoritative workflow supports the requested media, use a permitted general-tool ComfyUI route and attach its real prompt ID through `openh3_comfy_observe_prompt`; monitor and inspect that same result. An observation receipt is not native profile verification. If no supported route exists under a mandatory model constraint, report the specific evidence and unresolved capability.

For fixed-recipe runtime repair, call `openh3_comfy_install action=request intent=repair` with the selected family/profile in the existing generation conversation. The application derives a linked repair request and uses the current session approval; the original generation selection remains intact. `COMFY_INSTALL_INTENT_MISMATCH` on an older client is an integration defect, not a demand for another user authorization or a model-card visit. Once managed state is confirmed terminal, continue the same authorized repair with available general tools. Do not bypass a real permission denial or integrity requirement.

For graph/node/runtime metadata changes, keep the old profile intact. Register a real repaired workflow variant under a new profile ID, with the actual core/node revisions and supported bindings; do not invent a revision to pass `COMFY_NODE_REVISION_UNCONFIRMED`. Revalidate that variant with the original request and references. The application returns the validation result to this conversation. On success call `openh3_comfy_profiles action=adopt-repair profileId=<variant> jobId=<successful validation job>` to activate it in the existing generation request. This action requires real output validation and preserves the original model components and precision. Registration alone does not select the new variant. If the validation output fulfills the original creative request, present it; otherwise continue the original generation with that validated variant. Do not stop at a smoke test when the user's task remains unfinished.

If evidence proves the selected model cannot meet the requested capability, seek another compatible workflow, adapter or generation route that fulfills the user's goal. Where the user's instructions permit alternatives, proceed and explain the actual model/route used without requesting routine confirmation. Do not use adopt-repair to relabel different weights or precision as the original model. Preserve explicitly mandatory model constraints; report a concrete unresolvable conflict only after checking available supported routes. A failed URL or a fixed installer's limitation does not by itself establish such a blocker.

A profile is verified only after a representative successful generation and output validation; files, registration, or a queued validation job do not establish verification. When revalidation is needed, use `openh3_comfy_profiles` with `action: revalidate`, `profileId`, and representative `smokeInput`. The backend performs validation and records the result. Do not hand-register an invented profile or mark one verified yourself.

Generation and revalidation return `comfyJobId` and `job`; revalidation also returns `validation: true`. Keep the Agent turn active for every generation request, including a single image or video. Retain that same job ID and repeatedly use `openh3_comfy_job_status` with `waitMs: 30000` when supported until the actual terminal result. A wait timeout only ends that observation window; continue observing the same job. With older schemas, use bounded, spaced checks with backoff. Give concise conversation updates when the real phase changes, a repair starts, or a long wait needs explanation; never invent percentages or describe a running task as complete. Do not end the turn after submission or rely on a UI progress card to finish the user's task. At terminal success inspect the actual output, verify the requested media and constraints, present it in this conversation and continue any remaining authorized steps before the final reply. At terminal failure inspect the job/log and continue a supported repair under current permissions; a failed attempt is not the end of the goal. Avoid tight polling and duplicate generation. Use `openh3_comfy_cancel_job` for requested cancellation. A monitoring disconnect does not prove a job stopped; recover that job instead of submitting a replacement. Only an actual session/tool limit or explicit user request can interrupt this follow-through; then preserve the exact job ID and pending work for resumption.

`stopPolling: true` ends observation of a terminal failed attempt, not the user's goal. Follow `nextAction`: diagnose and continue permitted repair, recover an uncertain existing submission, or inspect successful artifacts. An unchanged repeated error requires diagnosis of the affected layer rather than another identical generation. Read the actual selected runtime's diagnostic log and interpreter evidence; an error code alone is not proof that the model or hardware is unsupported. For H3 acceleration startup errors, follow the runtime diagnosis section in the [H3 guide](references/h3.md) before resuming the original request.

If a profile query fails, inspect its inventory diagnostics and reuse existing state. Do not discard a working runtime or generate again merely because inventory is incomplete. If you need a direct ComfyUI HTTP fallback, retain the real `/prompt` response ID. Immediately call `openh3_comfy_observe_prompt` with that same prompt ID, loopback `baseUrl` and image/video `kind`. This read-only tool persists monitoring and returns a real `comfyJobId` so outputs appear in this chat, including after restart. It does not certify or register the model. Do not end the turn on raw API submission alone: wait for the observation handoff to succeed. If the tool is unavailable or rejects the handoff, monitor the same prompt through `/history/{promptId}`, retrieve the actual outputs via `/view`, save them locally, and attach images with Markdown using an absolute file path; link the actual saved video. Confirm decode and report actual completion or the concrete blocker. Never report only “submitted” and leave the user to find the result in ComfyUI. Do not resubmit to repair a missing result card.

Use the returned local output artifacts and actual terminal state as evidence. For errors, preserve the profile/job/operation ID and concise diagnostic details. Read `diagnosticLogPath` only for a relevant diagnosis. The backend owns bounded OOM recovery and resource cleanup; do not add a second retry loop or lower the original parameters. An exhausted unchanged-retry budget ends that job, not all diagnosis: a documented runtime repair such as supported CPU offload or tiled decode may be tried under existing authorization after checking terminal state, queue ownership and RAM. Record the material change, preserve required weights/precision and output requirements, validate the changed variant and its output, and stop unchanged repeated attempts. If no supported route meets the user's constraints, report that concrete conflict.
