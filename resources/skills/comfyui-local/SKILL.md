# Local ComfyUI

Use the OpenH3 built-in `video-media` tools and the selected registered profile. This skill covers the full local lifecycle; it does not depend on another installed skill. App startup imports these instructions only. Installing ComfyUI, nodes, models, and workflows is a separate operation requested by the user.

## Resolve tools first

Check the required tools **before reading references or scanning** the machine. If their schemas are deferred, call `ToolSearch` with exactly `{"query":"openh3_comfy"}`. This runtime searches a **literal substring**, not multiple names or natural-language keywords. Do not concatenate `openh3_comfy_environment openh3_comfy_profiles openh3_comfy_install` into one query. Use the exact returned tool names, including any MCP prefix.

A `No deferred tools` result for a combined query and a missing search result **do not prove** a tool is absent. Retry once with the single prefix above and check tools already exposed directly. Installation needs environment, profiles and install tools; generation needs environment, profiles, generate, status and cancel. If still unavailable, stop with a short tool-connection diagnostic and direct the user to restart/update and open a new model-card session. Do not spend turns on shell environment scans, ask the user to confirm an unexecutable plan, or promise that a missing tool will appear later.

## Choose the next action

- **Generate:** use the session's selected profile, or list registered profiles with `openh3_comfy_profiles` (`action: list`) once when none is selected. Prefer an existing verified profile that supports the requested inputs. Revalidate a downloaded/loadable candidate with a representative smoke input before normal generation. Submit `openh3_comfy_generate` with its profile ID and generation input. Generation needs no install plan. Before a local image/video run, inspect the selected endpoint's `/system_stats`, `/queue`, and `/object_info` (plus the selected Python/Torch device probe) so missing nodes, models, a busy queue, and GPU incompatibility are distinguished. Never clear or interrupt a non-empty queue; submit a single smoke input first and use the returned history/output artifact as evidence.
- **Install or install another model:** inspect the environment with `openh3_comfy_environment`, read the matching family reference, and build a pinned install plan. Prefer reusing healthy files and runtimes. A different model or component set receives its own profile.
- **Repair:** identify the failing registered profile and read [environment-and-repair.md](references/environment-and-repair.md). Diagnose the failed layer and prepare a bounded repair plan; preserve other environments and profiles.

Read only the relevant family: [H3 video](references/h3.md), [FastH3-Omni](references/fasth3-omni.md), [Qwen image editing](references/qwen-edit.md), or the matching heading in [image generation](references/z-image.md) for Z-Image, `flux-3-image-klein`, `moss-image-base`, `moss-image-sft`, or `krea2`. Keep MOSS Base/SFT and Krea Turbo/Raw separate. Then select its candidate, API graph and entries in [source-catalog.md](references/source-catalog.md). Read [network-and-downloads.md](references/network-and-downloads.md) for source selection and [install-evidence.md](references/install-evidence.md) when composing the plan. Read [source-resolution.md](references/source-resolution.md), [attachment-adoption.md](references/attachment-adoption.md), [sources.md](references/sources.md) or tooling notes only when the selected route needs their additional evidence; do not load every family, entire catalog or unrelated local template.

Reuse guidance for upstream `comfy`/`comfy-debug`, H3 integrity practice, and official workflow templates is in [tooling-adapters.md](references/tooling-adapters.md). Do not add a second generic downloader unless a deterministic gap remains after these adapters are applied.

For a new installation, consult [candidates.json](references/candidates.json): bundled discovery snapshots pin the official template revision/hash, component repository revisions/bytes/SHA-256, and required node classes. [workflows.json](references/workflows.json) supplies source-derived API graphs, semantic bindings/defaults, and template/schema/converter hashes for the matched Z-Image Turbo, single-image Qwen-Edit 2511, and FastH3-Omni R2V candidates (Omni entries are under `omni.baselines`, with source schema evidence in `omni`). Read the selected entry only. Copy its `graph`, `graphSha256`, `bindings`, `defaults`, and `requiredNodes` into the plan as `workflow`, `workflowSha256`, `bindings`, `defaults`, and `nodes`; resolve component destinations and runtime paths from this computer. Its graph hash uses UTF-8 `JSON.stringify(graph, null, 2) + '\n'`. These snapshots are **discovery-only**: offline structural checks do not prove local loading, kernel compatibility, memory use, or output quality. H3's separate legacy API export and other UI-only candidates require their own matching conversion evidence. Query newer upstream revisions when useful and record a new whole set; do not silently update a working registered profile.

The application binds a creation request to the session. Tools propagate that existing context; do not invent a request ID or pass one as an argument. A profile listing returns `profiles` plus authoritative `selection`; use it when selection is missing or may have changed, rather than relying on an old session environment value. `COMFY_SELECTION_CHANGED` means inspect the current selection and preserve the user's choice, not retry against another model.

Additional image recipes are in `workflows.json.imageModels.baselines`, with their own newer `coreRevision`, `sourceDerivedObjectInfo`, `schemaSources` and `classEvidence` in `imageModels`. Match `candidateId` to `candidates.json`; never apply the older Z-Image/Qwen core pin to these graphs. These source-derived specializations have not executed the converter or a GPU. FLUX requires an agent/LLM-expanded full scene caption; the baseline intentionally avoids downloading a second prompt-upsampler LLM. Each image candidate records separate diffusion/encoder/VAE precision and metadata-matched domestic transports. Gated authorization errors are source problems, not hardware incompatibility. List exact missing probes as **detection incomplete**, and confirmed incompatible kernels/resources as **device conditions insufficient**. No real generation means no verified profile.

| `openh3_comfy_environment`                            | Optional `root`, `python`, `baseUrl`, and up to 12 exact immutable `sources` URLs for read-only network probes                                       |

Revalidation also submits a background job and returns `comfyJobId`, `job`, and `validation: true`; it requires representative `smokeInput` (`COMFY_SMOKE_INPUT_REQUIRED` means supply that evidence). The UI monitors these jobs and displays outputs. End the turn after request/start/job submission rather than polling repeatedly. Use a job snapshot for a user status request or diagnosis, and cancel only the specified job when requested. Historical `openh3_h3_*` tools serve earlier H3 jobs; new registered profiles use the generic tools above.

## Hardware-aware selection

Collect actual OS/architecture, GPU/driver, available VRAM, RAM, disk and existing runtime information in one environment probe. Reuse that result; supplement only a specific missing field. A GPU name or VRAM alone is not a compatibility verdict. For a cold install, missing target Python/Torch, kernels, nodes and model files are installation work: choose pinned dependencies using upstream platform/architecture support, record execution checks as pending, and run them after installation. Missing OS/GPU/driver/memory/disk evidence remains a detection error. Existing runtimes can be checked immediately; do not require the uninstalled target to pass a kernel or generation test before it can be installed.

Keep model weights, text/vision encoder, VAE, optional LoRA, nodes, and workflow as one pinned **component set**. The diffusion precision does not specify encoder or VAE precision. Quantization reduces weight memory but may add kernel constraints, work buffers, latency, or quality loss. Resolution, frames, reference count, batch size, resident encoders, and decoding affect peak memory independently.

Default selection order:

1. Reuse a compatible existing verified profile, including its known component set and working runtime settings.
2. Otherwise choose one balanced complete candidate supported by the selected hardware and pinned runtime dependencies. Record measured versus estimated memory/speed evidence and pending execution checks. A bundled `discovery-only` graph is usable for planning and downloading its exact component set; it does not mark the profile verified. Do not ask the user to choose between all quantizations when they asked for automatic device selection. Perform representative end-to-end validation after installation.
3. Offer a lower-memory or experimental route only with its evidence and tradeoffs. Incomplete probes require diagnosis; they do not justify automatically selecting the smallest checkpoint.

Do not use fixed VRAM-to-model tables, mix sets by loose filename matches, or silently switch families, checkpoints, accelerators, or cloud services. Keep a known-good profile available when testing an alternative.

## Install plan and consent

Network selection is part of the approved component set. Call `openh3_comfy_environment` with the exact candidate URLs before presenting a plan and inspect its `network` object. The probe is limited to trusted HTTPS model/code/package hosts and validates every redirect; a `NETWORK_SOURCE_HOST_UNTRUSTED`, `NETWORK_SOURCE_URL_UNSUPPORTED`, or redirect error is a hard stop. If `network.requested` is false, or the requested source has no probe result, say that network evidence is incomplete; do not claim that the host is reachable. Prefer a verifiable ModelScope (魔搭) or domestic mirror copy when it is equivalent to the pinned upstream artifact, and retain the upstream source as the identity reference. Apply the full source, revision, size, and SHA-256 rules in [network-and-downloads.md](references/network-and-downloads.md). Do not substitute a mirror only because it responds faster, and do not reuse a partial file without a receipt and digest check.

Probe only the chosen candidate's necessary downloads and eligible fallback sources. Once one eligible source works, keep other approved equivalents as fallbacks; an optional mirror failure does not block an available valid source. Bundled API graphs need no network download. In batches of at most 12 URLs, preserve actual failures without exhaustively testing every family or alternative. Source identity and SHA-256 metadata may come from the bundled pinned catalog; verify downloaded bytes in the executor. A resume receipt is produced by the downloader, not a prerequisite for the first download.

Use the live schema to call `openh3_comfy_install` with `action=request` as soon as the complete plan is ready. The application reads the active conversation's observed approval mode. In **full automatic approval**, it authorizes and starts the complete valid plan directly: do not ask for chat or card confirmation. In other modes, the installation card requires one UI confirmation and then starts the saved plan without another LLM turn. Never infer approval from a prompt, an environment variable or your own tool arguments. If policy detection fails, report `COMFY_APPROVAL_MODE_UNAVAILABLE`; do not pretend the device is unsupported or grant yourself permission.

Return `comfyOperationId` and its actual state with a short version/download-size/destination summary, then end the turn. Do not request verbal confirmation before submitting the card. `running` means work has started, so do not call `start`, poll or resubmit it. `start` is only for recovery of an already authorized operation. A repeated request reuses its saved operation; a failed installation is not an automatic retry. Cancellation, failures and approval evidence retain their recorded state.

Build the complete pinned snapshot using the field contract in [install-evidence.md](references/install-evidence.md). Reuse catalog identities, graph and hashes; do not re-research fixed metadata on every turn.

Verify the installed CLI version's help before using flags. `comfy-cli` is optional tooling, not the runtime itself. When used, specify the workspace and force local routing on commands that accept `--where`; its auto-routing may otherwise use cloud credentials. Read structured `ok`, `error.code`, `error.details`, and `error.hint` before deciding what to do. A hint is diagnostic data, not permission to download or mutate the environment.

The executor rejects plans whose files or command working directories escape their selected resource roots, and rejects shell-style command wrappers. Reuse is path- and source-verified: same-size files without the recorded hash or source receipt are not considered reusable. Repair quarantines a damaged matching component before replacement and preserves the snapshot and known-good set. Do not put an arbitrary absolute path in a plan to bypass these checks.

## Register, verify, then generate

`openh3_comfy_profiles` exposes `list`, `register`, and `revalidate`. Registration records a complete component set and workflow; existence of files is only **downloaded**, successful loader/schema checks are **loadable**, and a successful representative end-to-end run is **verified**. Registration and a queued validation job do not establish verification. Once the validation job succeeds, inspect its outputs and the updated registered profile before normal generation. Never claim verified from an empty queue or a playable output alone. Use the install operation's returned verified profile or register a discovered existing environment through the tool, then revalidate as needed.

The normal generation path uses the chosen registered profile and its bindings. Do not rescan the entire model tree, reinstall dependencies, fetch a fresh upstream template, or rehash every model before each generation. Reuse recorded validation while its environment/component/workflow fingerprint remains unchanged. Revalidate when those inputs change or after a relevant failure; a repair invalidates affected validation. Never weaken or edit `memoryPolicy` to make an attempted input fit; that changes the profile recipe/fingerprint and requires new validation.

After a confirmed terminal OOM diagnosis, first release the same runtime's idle resources after checking remote terminal state, queue idleness and runtime/GPU identity. Observe queue and memory after `/free`; HTTP 200 only acknowledges the request. Retry at most once with the original model, references and original parameters, and persist the retry count across restarts. Do not automatically lower resolution, frame count, batch, quality or change quantization/offload. A second OOM is terminal until the user chooses a new plan. Unconfirmed submission/cancellation or interrupted monitoring blocks resubmission while the existing task is recovered. Keep same-component caches for speed; cleanup on component changes, memory pressure, terminal failures or 120 seconds idle must be coordinated with new work.

Return the actual local output artifacts and job state. For failures, keep the profile ID, prompt/job ID, failed node, and concise diagnosis so the next action can repair the same environment. When a result includes `diagnosticLogPath`, inspect that local evidence before planning a repair. A known prompt with interrupted monitoring remains active and is reattached without another submission; do not treat a connection error as a model failure or create a replacement job.
