# Prepare and choose workflows for one model

The model guide returns `recipe.workflow` for old baseline callers and `recipe.workflows` for every vetted variant of the selected candidate. `workflowMetadata` records task types, input roles/counts, adapter and recipe evidence. `preparation` lists shared component hashes, additional components and their byte count. These are preparation recipes, not local verification. Graph hashes use UTF-8 `JSON.stringify(graph, null, 2)` plus LF; source hashes describe the separately pinned original source.

## Installation

Keep installation Agent-led. Inspect and reuse matching weights, nodes and runtime, then prepare all `with-base` variants in the selected candidate. The zero-byte additional-weight variants share the same diffusion, encoder and VAEs; they do not justify copying weights or reinstalling a compatible runtime. Check each graph against the actual node schema. Validate the default route and compatible variants whose inputs and dependencies are ready, recording the exact tested roles/counts and environment. Leave an optional unavailable capability pending without invalidating a working base route. A capability explicitly requested now remains part of the active goal.

Call `openh3_comfy_resolve_workflow` with `{ "action": "prepare", "profileId": "<installed profile>" }` after registration/installation when the variant preparation result is not already available. This action writes vetted graphs against the registered existing weight files; it does not start a runtime or download a model. Inspect returned `pending` entries and their missing components/nodes before preparing dependencies. `action: "resolve"` is read-only and takes the original generation `input`; it does not itself install missing workflows.

Large control, patch or adapter dependencies are prepared on first use. The inventory's `unprepared` entries are research leads, not downloadable executable recipes. Resolve a matching supported graph, immutable source/version/hash, complete extra component list and byte counts before downloading. Reuse exact matching files. Changing a runtime requires its normal idle/ownership coordination. Store the completed variant alongside the original and continue the same request.

## Before generation

1. Interpret output type and each attachment's use. Distinguish `edit-source`, `identity`, `style`, `structure`, `first-frame`, `last-frame`, `mask` and general `reference`. Use stable reference IDs; a mask identifies its source through `maskFor`, with matching dimensions/orientation. Preserve original order. An attached portrait alone does not make a request ordinary image-to-image.
2. Call `openh3_comfy_resolve_workflow` with the current model selection, original input and task requirements. Prefer a locally verified compatible route, then a prepared route, then preparation under the same model/precision. Respect an explicitly fixed workflow. Use the tool's live argument schema; do not invent fields.
3. Distinguish missing required input, missing dependency, missing executable recipe, adapter gap and unsupported model capability. An absent installed route triggers preparation and validation of a supported recipe. Do not submit a known mismatched graph. Clarify only genuinely missing input or conflicting uses that cannot be inferred from the request.
4. Register the actual graph/hash and `workflowMetadata`, including its real binding slots, components and runtime/node versions. Do not copy another variant's execution evidence or set verified yourself. Submit the original request through the resolved profile; its successful result can validate the route and fulfill the user's goal together.
5. Supply generation identity as the top-level `attempt: { taskId, attemptId, predecessorAttemptId? }` alongside `profileId` and `input` to `openh3_comfy_generate`. Create one stable `taskId` for the requested output and one `attemptId` for its submission; the read-only resolve tool does not allocate these IDs. Repeated transport uses the same attempt. A confirmed failed attempt can be repaired with a new attempt linked through `predecessorAttemptId`; active or uncertain work must be recovered and observed, never replaced with a duplicate submission. Keep selection revision and workflow identity with the job. Stop or a changed goal ends the old continuation.

Qwen's two-image graph is statically checked against the pinned source-derived schemas; local multi-image execution and visual fidelity remain pending. Z-Image's single image execution evidence is preserved in [workflow-routing-evidence.json](workflow-routing-evidence.json), with its exact source record hashes, environment and tested scope. It is not this machine's verification. For H3, the file named `01_reference` has no reference input and is T2V; `04_i2v_fl2v` currently binds only the first frame and does not yet implement a last-frame pair.

The native media adapter supports FastH3-Omni video/audio references only. A capability label cannot bypass that check. A proven other-family route may use permitted general tools and `openh3_comfy_observe_prompt`, retaining the real prompt and original inputs. Observation does not confer native profile verification. Technical execution and decoded images do not prove identity fidelity, edit faithfulness or correct reference use; inspect the requested result separately.
