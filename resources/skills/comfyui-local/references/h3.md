# MiniMax H3 video

This family is MiniMax H3, including documented local ComfyUI routes. It is not HunyuanVideo. Start with an existing verified H3 profile before considering a different community acceleration route.

Model-card installation uses the shared `openh3_comfy_install` and active session approval policy. Full automatic approval starts a valid plan directly without another confirmation. For cold installs, measure the host and plan supported pinned dependencies; run the target kernels/loaders and representative video validation after installation. Missing target packages alone are not evidence of unsupported hardware. Historical H3 install tools are for earlier jobs, not a substitute for this selected profile.

## FastH3-Omni

FastH3-Omni is the separate `fasth3-omni` family. Read [its installation and generation guide](fasth3-omni.md) for the four pinned Comfy-native precision sets, hardware checks, domestic sources, ordered multimodal references and 8-step audio/video R2V baseline. Keep it separate from MiniMax H3 Turbo LoRA and the legacy MATLOWAI set.

## Components and route

A complete set includes diffusion weights, its text/vision encoder, ClipProj where required, video VAE, audio VAE for native audio, the matching Turbo/LightX2V LoRA where required, core/custom nodes, sampler settings, and the exact API workflow. Pin them together. The encoder may use a different quantization from diffusion, and the two VAEs may require different precisions.

[candidates.json](candidates.json) records the traced official INT8/Turbo8 candidate plus the application's historical MATLOWAI fused route as separate sets. Their same-named video VAE files have different sizes/hashes and sources; keep each set's exact VAE. The recorded official template/core commit is an inspected baseline, not proof of local kernel support. The historical set's component and node pins come from `h3OfflineBundle.ts` / `h3DownloadPlan.ts`, and require new profile validation before generic generation.

Use official local workflow templates as the baseline:

- `video_minimax_h3_t2v`: text to video.
- `video_minimax_h3_i2v`: an image anchors the starting state.
- `video_minimax_h3_r2v` / `video_minimax_h3_multiframe_reference`: reference-conditioned routes, only when the selected nodes and component set expose those capabilities.

`api_minimax_*` templates call hosted APIs and are outside this local profile. The template name is a discovery key, not a pinned source: obtain it from the official `workflow_templates` repository, record the fixed revision/hash, resolve subgraphs, and validate the API graph against this environment.

Rimagination's H3 Lite is a community implementation with matched sets and measured examples. Use its `references/component-sets.md` and `component-manifest.json` to discover complete candidates, not its example GPU labels as a selection table:

| Candidate     | Distinguishing components and validation                                                                                                                                                             |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| H3 Lite Set A | A-specific W4A8 diffusion, INT4 ConvRot text encoder, A-specific LightX2V LoRA, shared ClipProj and dual VAEs; compatible and accelerated workflows are separate variants                            |
| H3 Lite Set B | B-specific W4A8 diffusion, FP8-scaled text encoder, B-specific Turbo LoRA, shared ClipProj and dual VAEs; keep its matching compatibility baseline unless this runtime proves the acceleration chain |

Do not combine A's diffusion/LoRA with B's encoder/workflow based on similar filenames. Fetch the selected manifest at a fixed revision and verify its exact sizes/hashes. A same-size checkpoint may be corrupt. The words “portable”, “FP8”, or a laptop/desktop example in upstream documentation are not guarantees for the current computer.

An accelerated graph needs both node classes and executing kernels, including any Sage/Sol/chunked feed-forward/block-cache requirements. A compatibility graph is often a better balanced candidate when the fast chain is unproven. INT8 ConvRot, W4A8, FP8, BF16, and FastH3 variants have different loader/kernel/dependency needs. A FastVideo/vLLM runtime is not interchangeable with a ComfyUI profile; only select a ComfyUI graph supported by its documented components.

## Quality and capability validation

Estimate peak memory from frame count, canvas, references, resident encoder/ClipProj policy, attention, offload, and video/audio decode. Use measured evidence from the selected runtime when available. Lowering weight precision does not make all decode stages fit.

Start with a short clip and modest canvas accepted by the graph. Keep scheduler, sigma shift, steps, LoRA strength, and precision as the pinned workflow specifies. Distilled/accelerated and quality LoRAs may require different graphs; changing step count does not turn one into the other. Record each tested variant separately.

Bind the prompt, seed, dimensions, duration/frame count, optional images, and output prefix to real API node input names. If the application tool exposes `durationSeconds` but the graph accepts frames, store that supported conversion in the profile's actual bindings/runtime path; do not guess a node input. Confirm first/last-frame or multi-reference semantics before advertising them.

A representative smoke test verifies coherent moving frames, requested duration/dimensions, video decoding, and native audio when that capability is promised. Inspect multiple frames and audio streams. A successful sampler or playable MP4 can still contain frozen/mosaic frames or missing audio. Register **verified** only for the capability actually exercised.

For normal generation, use `openh3_comfy_generate` with the registered H3 profile. Describe the opening state, chronological motion, camera behavior, environment sound/actions/music, and invariants from references. An attached first frame anchors appearance; references need distinct roles. If a profile lacks a requested route, explain the missing capability and prepare an explicit compatible profile rather than silently substituting T2V.
