# Local image generation

Use the heading for the requested family. The additional image families below have independent profiles and recipes; the Z-Image instructions do not change their encoders, VAE, sampling or checkpoint identity.

All image families use the shared tool discovery and session approval policy in `comfyui-local`: full automatic approval starts a valid submitted plan directly; other modes use one installation-card confirmation. During a cold install, measure the host and assess pinned target dependency support first. Missing target Python/Torch, model files, loaders or kernels are installation steps; run their actual execution checks after installation before marking usable. Reuse the selected API baseline and completed probes; do not scan unrelated families or ask the user to choose every quantization.

## FLUX 3 Image Klein

Family: `flux-3-image-klein`. Start with the distilled generation checkpoint in the official [ComfyUI release](https://huggingface.co/black-forest-labs/flux-3-image-klein-comfy), not FLUX.2 Klein or the undistilled Base training checkpoint. The catalog pins three complete recipes: BF16 diffusion + BF16 Qwen3-VL-4B, INT8-ConvRot diffusion + INT8-ConvRot encoder, and NVFP4 diffusion + INT8-ConvRot encoder, each with the matching `flux2-vae.safetensors`. The newer fixed native core uses `CLIPLoader.type=flux3` and `EmptyFlux2LatentImage`; `flux2` is not a substitute loader type.

The `imageModels.baselines` graphs use Euler/simple, **16 steps, CFG 1**, with no distilled-model guidance embed and no Turbo LoRA. They expose text-to-image only. Editing, ten-reference input and bounding-box control are model capabilities, but require a separately pinned, bound and verified graph before advertising them on a local profile. Do not attach unbound reference images to this baseline.

**Prompt expansion is required.** Before generation, use the current agent/LLM to expand the user request into one complete scene caption: preserve subjects, counts, requested style, exact rendered wording, relationships, composition, lighting and intended edits; add coherent visible detail without contradicting the request. Submit the caption to the existing `prompt` binding. Do not pass an unexpanded short prompt and do not download an extra upsampler merely to expand text the agent can already write. These baselines intentionally remove the official optional local prompt-upsampler branch. A user who chooses the local upsampler needs a separate complete candidate, exact additional encoder, graph, memory budget and validation.

The official ModelScope repository exists but is gated; anonymous `repo/files` inspection returned 404 on 2026-10-22. Its published README uses underscore filenames whereas the pinned upstream snapshot uses hyphens. Do not guess the file mapping, revision or hashes. The shipped eligible transport order is the fixed-revision, metadata-matched `hf-mirror.com` copy followed by upstream. First recheck authorized ModelScope file metadata if access becomes available, adding it ahead of the mirror only after SHA-256/size identity is proved. A 401/403/hidden 404 is an authorization/source limitation, not evidence that the computer is unsupported. Do not bypass repository access requirements or put credentials in prompts, URLs or receipts. Use the existing supported authorized download mechanism or request a source-verified local file if an anonymous download is rejected.

NVFP4 requires a selected compatible **Blackwell** device and real loader/kernel evidence. The other formats also need actual precision and attention kernel checks; INT8-ConvRot availability is not proof that any older GPU will run the whole graph. Record the FLUX Kommunity License and separate encoder/VAE terms in the plan. Official [model guidance](https://huggingface.co/black-forest-labs/flux-3-image-klein/blob/main/README.md) and [Comfy instructions](https://comfy.org/flux-3-image-klein/) establish the family semantics; they are not this computer's validation.

## MOSS-Image-Base

Family: `moss-image-base`. Preserve **Base**, not SFT or an SFT acceleration LoRA. The [official Base model](https://huggingface.co/OpenMOSS-Team/MOSS-Image-Base) supports natural-language scene descriptions, tags and JSON layout prompts. The catalog uses [Comfy-Org's native single-file export](https://huggingface.co/Comfy-Org/MOSS-Image): BF16 diffusion + BF16 Qwen3.5-9B encoder; INT8-ConvRot diffusion + INT8-ConvRot encoder; or INT8-ConvRot diffusion + W4A8-GPTQ encoder. All use `flux2-vae_small.safetensors`. W4A8 requires its actual GPTQ/activation kernels and matching runtime dependencies; its smaller file size alone is not a compatibility result.

Use the image bundle's pinned ComfyUI revision containing native `moss_image` support. The official integration guide says `v0.41.3` lacks that support; a stable version label alone is insufficient. Verify the selected core revision, model recognition, actual `CLIPLoader.type=moss_image` enum and complete `/object_info`. The native route needs no MOSS plugin. Existing plugin workflows have different loader and timestep behavior: **do not carry their `ModelSamplingSD3` node into a native graph**. Native model sampling already uses shift 5; an intentional override uses matching `ModelSamplingAuraFlow`, not the old multiplier.

The shipped baseline follows the Base model reference: **Euler/simple, 50 steps, CFG 3, native shift 5**, empty negative prompt and `SkipLayerGuidanceDiTSimple` with `single_layers=22`, `double_layers=''`, `start_percent=0`, `end_percent=1`. The inspected UI template instead defaults to 25 steps/CFG 2.5 with SLG disabled; this deliberate reference-recipe specialization is recorded in `derivation`, not presented as unchanged conversion. Use positive dimensions divisible by 16, batch 1 for the representative smoke, and the matching VAE decode dtype. The 512-pixel smoke size is a starting input, not a measured memory limit.

Prefer the pinned **ModelScope → metadata-matched hf-mirror.com → upstream** transports. Every diffusion, encoder and VAE has a recorded fixed revision, byte count and SHA-256; do not swap a Diffusers directory, unrelated VAE or differently converted personal export by filename. Natural-language or JSON layout prompts feed the text binding; source-image editing and color/depth adapters are outside this baseline's capabilities. Keep dimensions consistent with any layout coordinates. See the [official native integration guide](https://github.com/OpenMOSS/MOSS-Image/blob/main/comfyui/README.md) for the native/plugin distinction. Model weights are Apache-2.0, with component terms retained in the plan.

## MOSS-Image-SFT

Family: `moss-image-sft`; card: **MOSS-Image-SFT**. This is OpenMOSS's supervised fine-tuned checkpoint, derived from MOSS-Image-Base. Keep its weights and profile separate from Base even though both use the native `moss_image` loader and the same Qwen3.5 encoder/VAE family. The pinned Comfy-Org/MOSS-Image set includes BF16 diffusion + BF16 Qwen3.5-9B, INT8-ConvRot diffusion + INT8-ConvRot encoder, and INT8-ConvRot diffusion + W4A8-GPTQ encoder. The SFT diffusion filenames are `moss_image_sft_bf16.safetensors` and `moss_image_sft_int8_convrot.safetensors`; do not silently substitute a Base checkpoint.

Use the pinned `image_moss_image_t2i.json` template and the SFT model reference settings: Euler/simple, 50 steps, CFG 3, native shift 5, empty negative prompt, and negative-branch SLG layer 22 across the full trajectory. The API baseline remains text-to-image only; layout and text rendering are supported by the model prompt format but require a separate validated workflow before being advertised as an additional capability. The SFT repository is Apache-2.0. Fixed ModelScope metadata and the verified domestic mirror are transports for the matching Comfy-Org/MOSS-Image artifacts; they do not establish local kernel or generation compatibility.

SFT needs the same runtime evidence as Base: actual `moss_image` loader support, matching precision/attention kernels, selected GPU and free VRAM/RAM, offload behavior and disk headroom. Report missing probes as **detection incomplete** and confirmed incompatibility as **device conditions insufficient**. Only a real SFT smoke generation with a decoded nonblank image and matching runtime fingerprint may mark its profile `verified`.

## Krea2

Family: `krea2`; card: **Krea 2**. Use the [Krea 2 Turbo](https://huggingface.co/krea/Krea-2-Turbo) generation checkpoint from [Comfy-Org/Krea-2](https://huggingface.co/Comfy-Org/Krea-2). Keep Raw/training checkpoints separate. Four full recipes are pinned: BF16 diffusion + BF16 Qwen3-VL-4B; scaled FP8 diffusion + scaled FP8 encoder; INT8-ConvRot diffusion + INT8-ConvRot encoder; NVFP4 diffusion + INT8-ConvRot encoder. Each uses the exact Krea `qwen_image_vae.safetensors`, not a same-named file from another profile without a matching hash.

The graph uses native `CLIPLoader.type=krea2`, the official `EmptyLatentImage` route, **Euler/simple, 8 steps, CFG 1** and zeroed negative conditioning. The optional style LoRA, prompt enhancer and UI switches are explicitly removed, so no unlisted LoRA or second LLM is required for the baseline. Style-reference LoRAs and image conditioning need a separate workflow, additional matching components and real validation; text-to-image does not imply general image editing. MXFP8 and Raw exports exist upstream but have no baseline in this bundle; do not advertise or select them as interchangeable with FP8/Turbo.

Prefer the catalog's metadata-matched **ModelScope → hf-mirror.com → upstream** transports, keeping per-file fixed revisions/bytes/SHA-256. Scaled FP8 needs the actual selected loader/backend to work: a software conversion path is a different performance claim from native FP8 arithmetic. NVFP4 requires compatible Blackwell and working kernels. Do not claim support from a dtype allocation or a small checkpoint. Preserve the Krea 2 Community License and all component terms in the plan.

## Device selection for the additional image families

1. Reuse a matching verified profile when its complete fingerprint is unchanged. Otherwise call `openh3_comfy_environment` and inspect OS/architecture, selected GPU/compute capability/driver, exact Python/Torch and CUDA/ROCm/MPS runtime, available precision/attention kernels, total/free VRAM and RAM, disk and permitted offload. Probe exact eligible download URLs, at most 12 per call; batch larger source sets. Fix compatible runtime package versions in the plan, rather than executing moving `pip install -U` examples.
2. Separate **detection incomplete** from **device conditions insufficient**. List missing probes, unknown device selection, missing import/kernel evidence or unverified network identity as incomplete; confirmed unsupported compute/kernel/runtime or measured resource deficit is insufficient. Include observed versus required facts and the candidate ID. Do not infer support from nominal VRAM or label all CPU/AMD/Apple/older NVIDIA devices supported or unsupported without a matching runtime route. If no compatible full set remains, explain the concrete deficit and stop installation planning for that device.
3. Compare full BF16, INT8 and optional accelerator-specific sets using actual evidence and a realistic budget for resident diffusion/encoder/VAE, activations, batch, output dimensions, offloaded RAM, runtime, download temporaries and output disk. Do not confuse aggregate download size with peak VRAM or force a candidate while detection is incomplete. These entries provide no measured minimum VRAM claims. A lower-memory candidate is a separate approved profile, never an automatic OOM quality downgrade.
4. Resolve the selected `candidateId` and `apiBaselineId` under `imageModels.baselines`. Copy the graph/hash/bindings/defaults and **its** core pin, resolve local component destinations and approved transports, prepare exact environment commands and a representative `smokeInput`, then submit through the shared observed session approval flow. Observe the real image's dimensions, decoding, coherent nonblank content, runtime/component fingerprint and peak memory. Only that successful full run permits `verified`/“Use model”. Retain failure-node/source diagnostics; keep the original single-retry OOM and shared-device cleanup policy.

## Z-Image

Use Z-Image profiles for local image generation supported by their registered workflows. The base and Turbo models have different sampling/training characteristics; select and pin a complete route rather than treating Turbo as a speed flag on any Z-Image checkpoint.

## Component selection

Discover official local templates `image_z_image_turbo` and `image_z_image` from `Comfy-Org/workflow_templates`. Inspect the chosen template at a fixed repository revision, including subgraphs and model metadata. Resolve and pin diffusion weights, the appropriate Qwen text encoder, VAE, core/custom-node revisions, and exact sampler settings together.

The traceable Turbo baseline in [candidates.json](candidates.json) records its template commit/hash, complete three-component repository revisions/bytes/SHA-256, and required node classes. It is discovery-only: authored core-version metadata is not a minimum supported version or a hardware compatibility result.

Its `apiBaselineId` selects `z-image-turbo-bf16-api-discovery` in [workflows.json](workflows.json). This ten-node API graph expands the official UI subgraph using the pinned converter and source-derived schemas. It retains the official 8-step `res_multistep`/`simple`, CFG 1, shift 3, Lumina2 text-loader type, and matching BF16 diffusion/Qwen encoder/VAE set. Copy the graph/hash, semantic bindings/defaults, and core pin into a cold plan after assessing this computer; resolve the candidate's exact three component destinations and runtime separately. No local ComfyUI installation is needed to read or prepare this graph.

Bindings expose prompt, seed, width, height, batch size, and output prefix. The shipped defaults are 1024×1024/batch 1; the suggested smoke input uses 512×512/batch 1. Neither is a measured memory budget or validated output on this computer. Only record a `memoryPolicy` after evidence supports the chosen limits and the same component set. This graph has no negative-prompt or offload binding.

The inspected official Turbo template references `z_image_turbo_bf16.safetensors`, `qwen_3_4b.safetensors`, and `ae.safetensors` in `models/diffusion_models`, `models/text_encoders`, and `models/vae`. These filenames help discovery; verify the current pinned source and hashes before any download. `ae.safetensors` is a generic filename used by other graphs, so its name alone does not prove the VAE is the matching file.

Treat FP8/scaled-FP8, GGUF, and other community quantizations as separate candidates with documented loader/node/runtime requirements. Confirm real accelerator and kernel support; successful dtype allocation or file loading alone does not prove the graph runs. Record diffusion precision independently from encoder/VAE precision and placement.

Choose a compatible balanced route using available memory, RAM/offload, target resolution, batch, and measured or sourced peak-memory estimates. Prefer an installed verified profile. Do not force a lower precision from a GPU's VRAM capacity alone. Turbo's distilled sampler/guidance/step settings come from its matching workflow; more steps or base-model guidance may reduce quality instead of improving it.

ControlNet/union, inpainting, LoRA, or upscale variants require their own matched graph and extra components. A plain text-to-image profile does not gain image-edit capability merely because the user attached an image. Inspect capability and input schemas before accepting that request.

## Register and reuse

Bind prompt, seed, dimensions, output prefix, and optional negative prompt only where the API graph exposes them. Resolve UI subgraphs into a valid API workflow using this environment's object schemas; an unresolved subgraph identifier is not an executable node class.

Run one modest image sample to validate the full text encoder → diffusion → VAE → output chain. Check dimensions, decoding, coherent content, nonblank output, and elapsed/peak-memory evidence. Record the exact component/workflow fingerprint and tested scale; larger canvases and batches require separate memory planning.

Normal generation calls `openh3_comfy_generate` using the selected registered profile and the user's prompt/dimensions. Keep its model identity and sampling defaults. Do not call a hosted `api_*` template, switch to Qwen, or install an alternative quantization as a retry without an explicit user choice. Diagnose bad images against loader identity, matching VAE, precision and sampler settings before changing checkpoints.
