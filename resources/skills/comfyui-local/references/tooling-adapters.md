# Reuse before inventing tooling

Use these upstream skills and references as narrow adapters for the Agent's installation plan. The fixed installer is optional, not a prerequisite for general tools. Choose execution from the actual environment and available commands, files, downloads and process tools; preserve SKILL.md's existing-operation and runtime-permission rules. Both routes preserve component identity and verification.

For a managed operation, the observed approval policy either starts the plan directly or requires one installation-card confirmation. Agent execution with general tools uses the actual runtime's normal tool approvals and existing grants. Neither route adds a separate chat-confirmation step.

## Agent execution with general tools

1. **Establish ownership and capability.** Recover any existing operation, download process, or ComfyUI prompt first. An active, awaiting-approval, or unknown task blocks a competing installer. Use this route directly for supported installation steps, or after confirming a fixed executor has stopped at a step it cannot handle. Changing executors does not resolve a real permission/source-access denial, integrity failure or unsupported device requirement. A backend `COMFY_TOOL_NOT_READY` code alone does not establish that no operation or partial installation exists.
2. **Plan and inspect the target.** Reuse context and completed probes. Record a short checklist with the live Plan/Todo tool when available, otherwise a local installation journal. Use permitted file/command tools to inspect configured or recent ComfyUI roots, OS, GPU/driver/architecture, available VRAM/RAM/disk, interpreter, and installed runtime. Do not scan entire disks. Missing target dependencies are installation work, not an unsupported-device diagnosis.
3. **Select and pin one complete set.** Read the relevant family and candidate/workflow records. Reuse a compatible API baseline or obtain a pinned authoritative template for installation/capability/compatibility repair. If identity, hash, schema or support facts are missing, continue bounded research; block only the affected step when required evidence cannot be established. General tools may bootstrap pinned runtime/nodes to obtain actual schemas, then complete and validate the API graph before generation. Only optional managed plan submission requires the full graph before approval. Never use a locally calculated digest of an untrusted download as its own expected upstream digest.
4. **Resolve sources and authorize execution.** Apply [source resolution](source-resolution.md) with the managed probe or equivalent permitted HTTPS probes, whether or not the managed probe is present. Prefer ModelScope, a verified domestic mirror, then upstream, with identical revisions/size/SHA-256. Managed host allowlists constrain those APIs; independently verified authoritative sources remain available through general tools under actual permissions. Preserve existing grants and license/access requirements; do not manufacture a card, approval mode, token, or request context. Keep authentication material out of command arguments, logs, URLs, and receipts.
5. **Install and transfer.** Use a dedicated target directory and the target runtime's interpreter; preserve existing user files and isolate conflicting dependencies. Use available download/package tools with fixed versions, `.part` files, resume metadata, bounded network retries, and final size/SHA-256 checks. Resume only when the source identity and server Range response match the receipt. Choose bounded parallel transfers for independent files; avoid concurrent writers to a file, Python environment, or node directory. Serialize dependent setup and shared GPU work. For long transfers, use supported background-process monitoring and saved process IDs/logs, or bounded resumable chunks, instead of exceeding a tool's timeout. A timeout does not prove that a process stopped. A hash mismatch stops the affected transfer and is diagnosed, not retried through another unchecked URL.
6. **Validate actual execution.** Check loader/node schemas and the exact API graph, then run one representative image/edit/video smoke input through the available supported interface. If using the local ComfyUI HTTP API, first inspect its queue and running work, wait for idle, never clear another task, and retain the returned prompt ID before monitoring history/output. Unknown submission, cancellation, or monitoring state requires recovery, not another submission. Decode the output and check motion/audio when promised. Do not add an untracked OOM retry loop or silently lower original parameters.
7. **Return the generation to this chat.** After a direct HTTP `/prompt` request, call `openh3_comfy_observe_prompt` with the same prompt ID, loopback endpoint and media kind. Its real `comfyJobId` establishes durable monitoring and the normal chat result card; it does not establish model verification. Do not end the turn on raw API submission alone. After observation attaches, keep the Agent turn active and monitor the same job with `openh3_comfy_job_status`, using `waitMs: 30000` when supported, until terminal output; report actual progress and inspect the output before finishing. If observation cannot be attached, monitor the same prompt's history, retrieve `/view` outputs, validate decoding and save the media locally. Include each image in Markdown with an absolute file path or link the actual saved video before reporting completion. Never resubmit just to obtain a result card.
8. **Keep an honest handoff.** Save the selected versions, target paths, expected hashes, receipts, completed/pending stages, process/prompt IDs, errors, and validation evidence in the installation journal without secrets. Resume by checking real files/processes/history. Do not invent OpenH3 operation/job IDs or edit its private database/profile registry. Discover/register/revalidate through supported interfaces when available; otherwise report the locally tested installation and the exact application-integration step still pending. Starting a process or downloading weights alone is not installation success.

| Reproducible ComfyUI environment recipes                                | [`comfy-build`](https://github.com/Comfy-Org/comfy-cli/tree/main/comfy_cli/skills/comfy-build) from `comfy-cli`               | Borrow its environment/build vocabulary when a separate Python environment is needed; do not let it choose an unpinned package index or bypass the local profile snapshot.                                    |

| Image workflow structure and node bindings                              | [`workflow_templates`](https://github.com/Comfy-Org/workflow_templates)                                                       | Reuse compatible graphs; installation or repair may fetch a pinned authoritative template. | Reachability, proxy, Range, and content-length evidence                 | Built-in `openh3_comfy_environment` with `sources`, or permitted equivalent HTTPS probes                                      | Probe exact candidate URLs. Read-only reachability does not establish model identity; compare receipts and hashes before selecting a mirror.                                                                  |
| Multi-shot H3 story planning                                            | `comfy-director` from `comfy-cli` (optional)                                                                                  | Reuse only its shot/continuity planning vocabulary. Every shot still resolves to a registered H3 profile and a fixed local API graph; it must not install a cloud route or invent model files.                |
| Showing a workflow/result in chat                                       | `comfy-relay` from `comfy-cli` (optional)                                                                                     | The desktop app already owns result cards and artifact paths. Do not add a second relay or upload local assets; use this adapter only when an external agent explicitly needs a presentation format.          |
| ModelScope/domestic mirror selection                                    | Local [source-resolution](source-resolution.md) playbook with the managed probe or permitted general tools                    | A downloader does not select identities for you. Probe, compare identity, resume with receipts, and preserve the actual runtime's approval policy.                                                            |

Do not copy upstream skill files into this bundle or run a competing downloader alongside an active managed operation. Reuse an available download tool or a small scoped helper when needed. A ModelScope or domestic-mirror helper must preserve the selected identity, recorded authorized sources, receipts, and checks; it must not silently rewrite a source or select a same-name file.

For a cold install, use these adapters when available: `comfy` for the pinned local workspace and command vocabulary, `comfy-custom-nodes` for node class and commit discovery, `comfy-build` for an isolated reproducible runtime recipe, and `comfy-debug` after a real log or `/object_info` failure exists. Missing optional adapters do not block equivalent work with permitted general tools. Keep source probing, mirror identity checks, runtime approvals, resumable receipts, and smoke validation. `comfy-director` and `comfy-relay` are optional planning/presentation adapters.
