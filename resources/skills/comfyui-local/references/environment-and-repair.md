# Environment diagnosis and repair

## Probe the runtime that will run the graph

Separate host detection, install planning and post-install execution checks. During cold planning, the host OS/GPU/driver/memory/disk must be known, while missing target Python/Torch, kernels, nodes and weights are expected installation steps. Use the target dependencies' pinned upstream support evidence now; run actual imports, kernels, loader schemas and representative generation after those dependencies exist. Inspect an already installed runtime immediately when available. Avoid re-running completed probes or scanning unrelated disks/templates.

Start with `openh3_comfy_environment`. Reuse the registered profile's paths and check tool results before supplementing missing fields. For an install or a repair that may download files, pass the exact immutable model, node, package, or workflow URLs in `sources` and read the returned `network` object. A nonzero process exit, missing command, permission error, timeout, missing source result, or `NETWORK_*` issue is incomplete evidence, not evidence of no accelerator or a usable mirror. Avoid searching every disk; inspect configured roots and user-named locations first. A cold plan may record a CPU route only when the selected graph/runtime explicitly supports CPU and the plan uses its CPU launch mode; otherwise GPU/kernel evidence is required.

Collect an evidence record:

| Layer          | Evidence needed                                                                                                                   |
| -------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| OS and process | OS/architecture, native Windows versus WSL/Linux, actual executable paths, environment root                                       |
| Accelerator    | Device identity and adapter index, driver, free/total memory, torch backend and device capability                                 |
| Python/runtime | Selected interpreter/version, torch version and compiled CUDA/ROCm backend, device availability, node imports                     |
| Kernels        | Required attention/quantization implementation imports and small execution on this device; package presence alone is insufficient |
| Memory/storage | Available RAM, virtual memory/offload space, free bytes on the target volume, model download and extraction sizes                 |
| ComfyUI        | Local endpoint, version/commit, startup log, `/system_stats`, `/object_info`, required loader choices and node schemas            |
| Profile        | Exact component paths/revisions/hashes, workflow hash, input bindings, capabilities, last validation fingerprint                  |

For NVIDIA, `nvidia-smi` can supplement device/driver/free-memory evidence but does not prove the selected Python has working CUDA. For Apple, AMD, or Intel, inspect the runtime's backend and required kernels; do not infer support from GPU enumeration. CPU fallback may be considered if the exact graph supports it and its estimated latency and RAM use fit the user's goal.

Keep interpreters isolated. Invoke the profile's Python explicitly; a global `pip` or another environment's `comfy` may report success while changing the wrong runtime. Do not replace a user's healthy environment or update every custom node just to install one family. Use a separate target root/profile when dependency sets conflict.

Installation boundaries are part of the plan evidence. Use a dedicated non-volume-root `targetRoot`; a cold install puts `environment.root` in its ComfyUI child. The executor creates the parent after consent. Workflow/component destinations, `.part`, `.resume.json`, `.comfy-source.json`, and command `cwd` must resolve under `targetRoot`, `environment.root`, or an explicitly declared `launchArgs --models-directory` (also `--models-directory=...`). The nearest existing ancestor's realpath is checked, including junction/symlink escapes. Declare external reusable model roots explicitly. Existing assets are reusable only after expected source receipt/hash and recorded size match. Verified reuse may make their `downloadBytes` zero; `requiredBytes` still covers new runtime, temporary, extraction, and output needs. Repair snapshots and quarantines a damaged matching file before restoring the same pinned set.

The executor accepts bounded installation commands:

- `git`: clone/fetch and fixed checkout/switch/reset, plus revision/status reads; clone uses HTTPS with a fixed branch/revision or a subsequent fixed checkout, and its destination is scoped to the plan roots.
- `comfy`: `--workspace` must equal `environment.root`, `--where` can only be `local`; runtime install uses `--version`, `--commit`, or `--comfyui-version` matching the recorded revision; node installation targets include `@revision`; workflow commands are only `validate`/`print`.
- Exact target Python: `-m venv`, `-m pip` with `install`/`check`/`show`/`freeze`/`list`, or `-m comfy_cli`. Its same-directory pip has the same package/path constraints. Package versions are explicit `==` pins, or requirements/local projects reside inside the scoped roots. Arbitrary scripts, `-c`, and other modules are not accepted.
- A distinct already-existing bootstrap Python is allowed only for `-m venv` whose target contains `environment.python`; it cannot install packages into the bootstrap. `uv venv --python` can use that interpreter, while `uv pip` must target `environment.python` via `--python`. The executor confirms interpreter identity with read-only probes.

Use argument arrays, never shell syntax or unknown executables. A revision label does not make an arbitrary command valid. Read-only offline conversion before requesting consent is separate from these installation command limits.

## Validate once, then reuse

Before the end-to-end smoke test, check component identities and hashes, required class types, loader enums, workflow links, input binding types, and output nodes. If the template is UI-format JSON, obtain an API export or convert against `/object_info` from this same runtime. New templates may need a newer core than an installed stable release; verify node support before planning a version change.

### Prepare a cold installation without starting or installing a runtime

A missing target ComfyUI/Python is expected for a cold installation. Separate that expected absence from incomplete OS, accelerator, kernel-support, memory, or disk evidence. Probe installed interpreters and the accelerator read-only; plan exact runtime dependencies from upstream support evidence, and defer their actual execution checks to the consented installation's validation stage. Do not install a temporary runtime merely to prepare the plan.

The plan must already contain an API graph. For the matched Z-Image Turbo or single-image Qwen-Edit 2511 candidates, read the entry identified by `apiBaselineId` in [workflows.json](workflows.json). It includes the API graph, bindings/defaults, every executed class schema and fixed source/hash, original converter output, and explicit specialization evidence. Copy the graph with its exact component set and core pin; map the candidate components to absolute model destinations. A missing target runtime does not prevent this read-only planning. The graph hash is UTF-8 `JSON.stringify(graph, null, 2) + '\n'`; preserve it when copying the graph. Planning defaults and smoke sizes have not been tested on this computer.

For other routes, prefer a pinned upstream API export or convert the pinned UI template using a matching offline `object_info` dump or source-derived schema. Preserve actual input names/order, optional inputs, widget types/defaults, loader choices, return types, output flags, and subgraph wiring; do not infer them from widget labels. A source-derived enum describing planned assets is not evidence that those assets are installed.

At the recorded comfy-cli revision in [candidates.json](candidates.json), `comfy_cli.workflow_to_api.convert_ui_to_api(workflow, object_info)` accepts an explicit schema dictionary and expands subgraphs without a running ComfyUI server. This is an optional offline conversion route, used only when that pinned tooling is already available or its source can be inspected. Its `workflow validate --workflow <api.json> --input <object_info.json>` supports offline structural checks. Verify the installed version's help before using flags. `workflow print` is a display aid, not an API export; `run --print-prompt` may still fetch schemas when its input is UI-format.

Record in the plan's `evidence` the fixed template/source revisions and hashes, schema file hash and provenance, converter revision/hash, resulting API graph hash, reviewed classes/bindings, and offline check result. Mark this as planning evidence, with local loading and smoke validation still pending. The historical MATLOWAI H3 candidate already references a pinned API graph; the official H3 UI-only candidate still needs its own conversion evidence. If a required schema or faithful conversion is unavailable, diagnose that missing input before proposing an executable plan.

Install `prepare` steps build the pinned runtime/nodes, then download exact components; `finish` steps may confirm the previously planned conversion. The executor persists `plan.workflow` as the approved graph, so a `finish` command must not supply a different graph after consent. Once installation creates the target runtime, validate against its live `/object_info` and run the representative smoke job before declaring the profile verified.

Run a small graph that exercises the intended path: text generation, image editing with a source image, or video with the chosen reference/audio mode. Before submission, inspect `/system_stats`, `/queue`, and `/object_info`; if the queue is non-empty, wait for the selected profile's work and do not clear, cancel, or enqueue behind another user's task. Submit one image or one short video smoke input at a time, retain its prompt/job ID, and read the returned history record. Record the actual output path(s), seed, dimensions, duration, steps, prompt ID, elapsed time, and peak-memory measurements where available. Clearly label memory/time estimates and their source. Inspect image decoding, coherent moving frames, and native audio where promised; a successful HTTP response or non-empty history without the expected output file is not success. A low-resolution smoke run validates that scope, not every larger resolution or longer duration.

Media checks decode distributed video frames, reject frozen/blank output, and compare explicitly bound dimensions/duration. Declare `native-audio` only when the graph promises generated audio; its smoke output must include a decodable audio stream. These checks establish technical execution, not prompt fidelity or edit preservation, which still require reviewing the actual result. Failure results expose `diagnosticLogPath` for bounded local startup/execution evidence; read that file rather than inferring a dependency fix from a generic error code.

Explicit `openh3_comfy_profiles` revalidation requires `smokeInput` and returns a background validation job, not an immediately verified profile. Preserve its `comfyJobId` and `validation: true`; the UI observes progress. After success, check the updated profile and relevant output before generating. Cancelling or failing that validation does not prove readiness.

Cache large-file validation by path, size, modification metadata, and recorded hash. Invalidate it after changes or a corruption diagnosis. The registered profile is the reusable unit. Revalidation should target changed/failed assets and the selected workflow rather than silently choosing another set.

## Repair the failed layer

| Symptom                                  | Next diagnostic action                                                                                               | Bounded repair                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server not running                       | Check selected interpreter/root, startup exit/log, endpoint and port ownership                                       | Launch the registered runtime with its pinned arguments; investigate startup imports before reinstalling                                                                                                                                                                                                                                                                                                                   |
| Missing class or rejected node           | Read `/object_info` and per-node validation errors; distinguish absent pack from failed import/version mismatch      | Install or repair the exact required pinned node/core version, restart the selected server, refresh schemas                                                                                                                                                                                                                                                                                                                |
| Missing model enum                       | Read the loader's choices and resolved model paths                                                                   | Correct the binding/path or install the exact component from the same set                                                                                                                                                                                                                                                                                                                                                  |
| Torch/kernel import or execution failure | Check Python/torch/backend/driver/device capability and the failing kernel's upstream support                        | Replace only the incompatible dependency or use a separately validated compatible workflow variant                                                                                                                                                                                                                                                                                                                         |
| OOM or process crash                     | Identify failed node, allocation stage, GPU/runtime identity, contention, RAM/virtual memory and original parameters | Confirm terminal remote state and queue idleness, release this runtime's idle resources, then observe memory/queue changes. Retry OOM once with the same model, references and original parameters; persist the count. Never automatically lower quality, canvas, frames, batch or change offload/quantization. A second OOM is terminal until the user chooses a new plan; recover ambiguous jobs before any resubmission |
| Mosaic/gray frames, NaNs, wrong colors   | Check hashes, diffusion/encoder/VAE/LoRA set, precision, scheduler/sigma settings, unsupported patches               | Restore the matched pinned set or baseline graph; do not cover corruption with more steps                                                                                                                                                                                                                                                                                                                                  |
| Video missing motion/audio               | Inspect decoded frames, audio streams, graph outputs and encoder muxing                                              | Repair the selected graph's video/audio path; a playable MP4 alone does not pass                                                                                                                                                                                                                                                                                                                                           |
| WebSocket timeout/disconnect             | Query the existing prompt ID's queue/history before resubmitting                                                     | Reattach or retrieve outputs; avoid duplicating a still-running job                                                                                                                                                                                                                                                                                                                                                        |
| Download partial/wrong data              | Inspect HTTP status, expected size/hash, HTML/error body, partial-file ownership                                     | Resume only a matching partial file or replace that component through a consented repair plan                                                                                                                                                                                                                                                                                                                              |

Repair requests use `openh3_comfy_install` with `repair: true`, a full replacement snapshot, and the same request/consent/start contract. State the exact affected profile and components. Preserve the known-good set and outputs. Do not stop another application's GPU process, clear another user's queue, or alter an unrelated environment as an automatic repair step.

After repair, revalidate the affected profile and record the result before reporting it fixed. If the diagnosis is still incomplete, report the concrete missing evidence rather than repeatedly downloading or changing models.
